## 1. 先看问题

「测试」和「打包」看着不相干，但在本项目里被同一个约束逼到同一条路上：
**开发机是 Windows 上跑着安全软件、沙箱和文件索引工具的受限环境。**
两处的解法因此是同一种思路：**不跟环境较劲，换一条根本不会碰到它的路。**

- **测试**：最自然的写法是 `node --test`，但那个运行器**为每个测试文件 spawn 一个子进程并把
  stdio 接管道**（`src/test/run-tests.ts:4-5` 的原文），受限环境里管道就是被拒的那件事 ——
  测试一条都跑不起来。本项目改成同进程 `import` 全部测试文件（`src/test/run-tests.ts:11-41`）。
- **打包**：产物里的 `.asar` 会被本机常驻进程（火绒 / Everything / Windows 搜索）解析并
  **长期持有句柄**：能读、不能改名、不能删除（`electron-builder.yml:46-48`）。
  而打包的第二步恰好要删掉上一次的产物 —— 删不掉就整个中断。
  本项目改成让产物里**根本不出现** `.asar`（`scripts/package.mjs:25-35`）。

## 2. 核心概念

### 2.1 测试入口不是运行器，只是一张 import 清单

`run-tests.ts` 里没有一个断言，只有 18 行 `import "./xxx.test.ts"`。
`node:test`（Node 内置模块）在**被 import 时**就注册并执行 `test()`，不需要 CLI 去"发现"测试文件 ——
既然执行由 import 触发，"哪些文件要跑"就由这个入口决定。它用分组注释（M1 / M3 / M4 / …）
排开 18 个文件（`src/test/run-tests.ts:11-41`）。

### 2.2 原生 TypeScript 类型擦除

Node ≥ 22.18 能直接执行 `.ts`：把类型标注**原地删掉**再跑，不做类型检查、不生成 `.js`——
所以 `pnpm test` 就是 `node src/test/run-tests.ts`（`package.json:22`）。
因为只是删字符，任何**需要生成新代码**的语法都用不了：`enum`、`namespace`、
构造函数参数属性都不行（`tsconfig.json:16` 的 `erasableSyntaxOnly: true` 把这条限制交给 `tsc` 守）。

### 2.3 应用归档 `.asar`

Electron 的应用归档格式：开头一段 JSON 索引（每个文件的路径、偏移、大小），
后面**首尾相接**拼接每个文件的原始内容 —— **默认不压缩**。
把几千个小文件合成一个，安装/启动更快，源码也不容易被随手翻看。
本项目**故意不用**它：`electron-builder.yml:55` 是 `asar: false`，应用以 `resources/app/` 明文目录存在。

### 2.4 `resources/app.asar` 与 `resources/default_app.asar` 是两样东西

| | `resources/app.asar` | `resources/default_app.asar` |
| --- | --- | --- |
| 谁的代码 | **我们的**启动器（`out/` 三份产物 + `package.json`） | Electron 发行包**自带**的 |
| 干什么用 | 就是应用本体 | 「没给 app 时」启动的空壳应用（兜底） |
| 本项目里 | 被 `asar: false` 换成 `resources/app/` 目录 | 被 `.electron-dist` 镜像**跳过**，压根不进产物 |

**我们永远自带 app，所以用不到 `default_app.asar`**；而它正是卡住下一次打包的那个文件
（`scripts/package.mjs:13-14`）。

### 2.5 过滤镜像 `.electron-dist`

`node_modules/electron/dist` 的镜像，**跳过 `resources/default_app.asar`**，其余文件用 NTFS
**硬链接**指过去，所以不占额外空间（`scripts/package.mjs:29-32`）。
之所以不直接删那个源文件：它自己也常被锁住（`scripts/package.mjs:31-32`）。
生成逻辑在 `scripts/package.mjs:338-359`，由 `electron-builder.yml:34` 的 `electronDist` 指过去。

### 2.6 便携版的 `PORTABLE_EXECUTABLE_DIR`

单文件便携版**每次启动把自己解压到 `%TEMP%\<随机名>\`**，electron-builder 为此注入
`PORTABLE_EXECUTABLE_DIR` = 便携 exe 真正所在目录。不用它的话配置会写进临时目录，
而下次启动解压出的目录名又不一样 —— 用户看到的现象是
**「便携版每次启动配置都被重置」**（`src/main/paths.ts:36-39`）。
解析它的是 `resolveAppDir`（`src/main/paths.ts:46-56`），由 `src/main/index.ts:61-64` 调用。

## 3. 代码怎么走

### 3.1【测试】为什么不用 `node --test`

```ts
// src/test/run-tests.ts:1-9
/**
 * 测试入口。
 *
 * 为什么不用 `node --test`：那个运行器会为每个测试文件 spawn 一个子进程并把 stdio 接管道，
 * 在受限沙箱里会直接 EPERM。这里改成在同一个进程里 import 全部测试文件，
 * node:test 会自动执行并设置退出码 —— 不依赖子进程，也不需要任何测试框架。
 */
```

三个要点：**`EPERM` 不是权限配置问题**，而是"受限环境不允许开管道"这条硬边界；
**`node:test` 与 `--test` 是两件事** —— 前者是内置模块（`import { test } from "node:test"`），
后者是会开子进程的 CLI 运行器，本项目只用前者；**没有测试框架** ——
`package.json:37-52` 里没有 Jest/Vitest/Mocha 之类的任何依赖。

### 3.2【测试】新增测试必须进这张清单

最容易踩的坑：**光把文件放进 `src/test/` 什么都不会发生 —— 必须被 `run-tests.ts`
import 一次，它的 `test()` 才会注册。** 组织方式是手写分组注释，不是目录扫描：

```ts
// src/test/run-tests.ts:11-41（节选，实际 18 行 import）
// ---- M1：core 层 ----
import "./helpProbe.test.ts";
...
// ---- M4：环境自检 ----
import "./precheck.test.ts";
import "./paths.test.ts";
...
// ---- 模型目录扫描（单模型模式的下拉框）----
import "./models.test.ts";
```

核对方法：`src/test/` 里 `.test.ts` 的个数应等于这里的 import 行数（当前两边都是 18）。
注意 import 路径**带 `.ts` 后缀** —— `tsconfig.json:15` 的 `allowImportingTsExtensions: true`
就是为它开的（擦除模式下路径必须指向真实文件，没有"编译后变 `.js`"这一说）。

### 3.3【测试】`.ts` 直接跑带来的三条写法约束

取 `src/test/args.test.ts:1-11` 的 import 段：第 5 行导入真会执行的 `buildArgs`，
第 8 行则是 `import type { BuildInput, BuildResult, LauncherConfig } from "../core/types.ts"`。

- **`import type` 不是风格问题**：类型在运行时被完全擦掉，写它等于显式声明"这行只给编译器看"。
  `tsconfig.json:13` 的 `verbatimModuleSyntax: true` 会把写错的写法变成**编译错误**，而不是靠自觉。
- **`import.meta.dirname`**：原生 ESM 的"当前文件所在目录"（代替 `__dirname`），
  测试文件用它算相对路径去读 `fixtures/`（`src/test/args.test.ts:10`）。
- **没有 `enum`**：`src/` 里 grep `enum` / `namespace` 一处都没有 —— 它们需要生成运行时代码，
  擦除模式跑不了（`tsconfig.json:16`）。

### 3.4【测试】覆盖策略：纯函数优先 + 真实 fixture

一句话：**把判断逻辑做成纯函数，测试只喂输入、断言输出；不吃纯函数的那些（解析真实文件、
跑真实环境）就用 fixtures 或 skip 条件。** 数据上也看得出来：18 个文件共 192 个 `test()`，
而 `package.json:37-52` 里**没有任何 mock 库**。

**（1）`args.test.ts`：对照命令行的黄金用例。** 最硬的一条把整个 `argv` 数组逐字节对拍 ——
因为 `README.md:196` 的验收标准是「同一份配置，`args` 输出的命令行必须与既有
`llama-oneclick.ps1` 生成的逐项一致」，参数顺序和 `-t 6` 这种简写形式都是行为的一部分：

```ts
// src/test/args.test.ts:105-115（节选）
  assert.deepEqual(r.argv, [
    "--host", "127.0.0.1",
    "--port", "8080",
    "-m", "E:\\Code\\llama\\models\\qwen2.5-7b-instruct-q4_k_m.gguf",
    "-t", "6",
    "-c", "16384",
    "-n", "8192",
    "-fa", "on",
    // ...（后面还有 KV cache 量化、jinja、采样等项）
  ]);
```

```ts
// src/test/args.test.ts:125-126
assert.deepEqual(r.warnings, [], `不该有告警：${r.warnings.join(" | ")}`);
assert.deepEqual(r.env, {});
```

第二条展示**同一个开关在不同版本走不同形式**：新版是 `-fa on/off/auto`，旧版是纯开关。
它断言的不是"旧版该怎么传"，而是 **`-fa` 后面绝不能跟着 `on/off/auto`** ——
这正是"新语法泄漏到旧版本"这个 bug 的形态：

```ts
// src/test/args.test.ts:204-213（节选）
const r = build(base(), { caps: createCapabilities(oldHelp) });
const next = r.argv[r.argv.indexOf("-fa") + 1];
assert.ok(
  next === undefined || !["on", "off", "auto"].includes(next),
  `无占位符的旧语法不能传 on/off/auto，实际后面跟了 ${next}`,
);
assert.equal(r.steps.find((s) => s.key === "flash_attention")?.reason, "cli");
```

最后一行还把决策表里的原因（`reason === "cli"`）纳入验证（详见第 05 章）。

**（2）`paths.test.ts`：路径决策，用注入桩 + 真临时目录。**
`C:\Program Files` 在本机**不可能真去写**，所以只读场景靠注入 `canWrite: () => false`
（`src/test/paths.test.ts:46-52`）；断言的是"退回 userData"这个**决策结果**
（`src/test/paths.test.ts:54-56`），因为决策错了的后果很具体：应用连缓存都写不了。
另有用例证明**不注入时也会真探测**（`src/test/paths.test.ts:59-70` 用 `mkdtempSync` 造真实目录）。
而便携版那条把 bug 的形态直接写进了输入：

```ts
// src/test/paths.test.ts:80-87
test("resolveAppDir：单文件便携版用 PORTABLE_EXECUTABLE_DIR（不能用 %TEMP% 里的解压目录）", () => {
  // 实测：便携版每次启动都解压到 %TEMP%\<随机名>\，app.getPath("exe") 指的是那里
  const dir = resolveAppDir({
    portableExecutableDir: "E:\\llama-launcher-dist",
    exePath: "C:\\Users\\feng\\AppData\\Local\\Temp\\3JDpNFX2tCZGwr9Q\\llama-launcher.exe",
  });
  assert.equal(dir, "E:\\llama-launcher-dist");
});
```

`exePath` 特意写成 `%TEMP%\<随机名>\` 的样子；断言结果是环境变量那个目录，
等于把"配置写哪儿"这个用户可见行为钉死了。

**（3）`precheck.test.ts`：检查项用"改一个字段"覆盖分支。** 它先造一份"一切正常"的事实，
再逐项改（`src/test/precheck.test.ts:28-33` 的 `facts()`）：

```ts
// src/test/precheck.test.ts:205-210
const item = itemById(buildPrecheckItems(facts({ modelSizeMiB: 14600, vramTotalMiB: 16380 })), "model-vram");
assert.equal(item?.level, "warn");
assert.match(item?.title ?? "", /KV cache 放不下/);
assert.match(item?.suggestion ?? "", /--n-cpu-moe|IQ2_M/);
```

判据是一条比例阈值，但**用户看到的文案分两种情形** —— 同一个测试紧接着改了
`modelSizeMiB` 再断言措辞变成 `/已超过显存/`（`src/test/precheck.test.ts:211-213`），
所以用 `assert.match` 核对**措辞**而不只是 `level`。第三行还要求建议里必须有出路
（`--n-cpu-moe` 或换 `IQ2_M`）—— "只报警不给办法"算不合格。

**（4）跑不动的用例用 `skip`，不是删掉。** 依赖本机真实环境的用例带条件跳过，例如
`{ skip: existsSync(realExe) ? false : "本机没有 llama.cpp，跳过" }`
（`src/test/precheck.test.ts:275-278`）。它依赖 `..\..\..\llama.cpp\llama-server.exe`
（路径见 `src/test/precheck.test.ts:23-26`）：别人 clone 下来没这些文件时应该是"跳过"而不是"失败"，
否则新人的第一次 `pnpm test` 就是红的。

### 3.5【测试】`pnpm test` 与 `pnpm typecheck` 各守一半

| | `pnpm test` | `pnpm typecheck` |
| --- | --- | --- |
| 命令 | `node src/test/run-tests.ts`（`package.json:22`） | `tsc --noEmit`（`package.json:23`） |
| 守什么 | **行为正确性**：命令行拼得对不对、路径决策对不对 | **类型正确性**：字段名、可空性、`import type`、擦除约束 |
| 谁来判 | `node:assert/strict` 断言 + `node:test` 退出码 | `tsc` 的 0 错误（`tsconfig.json:11` 的 `noEmit`） |
| 典型漏网 | 类型标错但运行恰好正常的分支 | 所有执行不到的行 |

**为什么两个都要跑**：类型擦除意味着类型错误**不会阻止 `pnpm test` 跑起来** ——
`test` 全绿也可能有 20 个类型错误。反过来 `tsc` 一行都不执行，
`assert` 里的期望值写错了它完全看不见。我写这章时在本机实测跑过一次：

```text
$ node src/test/run-tests.ts
# tests 192 / # pass 192 / # fail 0
```

（退出码由 `node:test` 自动设置：失败就非 0，所以 `pnpm test` 能直接用在 CI 里。）

### 3.6【打包】三段构建：`electron.vite.config.ts`

```ts
// electron.vite.config.ts:10-23（节选）
 *   main     —— ESM（Electron 44 支持 ESM 主进程）
 *   preload  —— CJS，文件名固定 .cjs（package.json 是 type: module，.js 会被当成 ESM 而 preload 需要 CJS）
 *   renderer —— React + Tailwind
 *
 * ⚠ `electron` 必须显式列入 external：
 *   electron-vite 的 externalizeDepsPlugin 只外部化 package.json 的 dependencies，
 *   而 electron 装在 devDependencies 里。不外部化的话，rollup 会把 electron 这个 **npm 包**
 *   整个打进 bundle —— 那个包的 index.js 在 load 时会去解析自己的二进制路径，找不到就现场下载，
 *   结果就是应用一启动就报 "Electron failed to install correctly"。
 *
 * core（src/core）不打进渲染层：界面只能通过 IPC 拿到数据，保证「界面不改命令行」。
 */
```

三段的落点与格式（`out/` 就是 `files: out/**/*` 打进去的东西）—— main 是
`outDir: "out/main"` / `format: "es"` / `entryFileNames: "index.js"`，preload 是
`outDir: "out/preload"` / `format: "cjs"` / `entryFileNames: "index.cjs"`
（`electron.vite.config.ts:26-32`、`38-43`，两段都写了 `external: ["electron"]`）。
主进程按文件名硬找这两份产物（`src/main/index.ts:37-38`）：`../preload/index.cjs` 与
`../renderer/index.html`。两个"为什么"：

- **preload 为什么必须是 `.cjs`**：`package.json:7` 是 `"type": "module"`，
  这个目录下 `.js` 会被当成 ESM，而 preload 需要 CJS 形式加载，所以显式改名消歧义。
- **`electron` 为什么必须 `external`**：`externalizeDepsPlugin()` 只外部化 **`dependencies`**，
  而 `electron` 在 `devDependencies`（`package.json:44`）。不额外写 `external: ["electron"]`
  就会把整个 npm 包打进 bundle，启动时报 `Electron failed to install correctly`。

### 3.7【打包】`electron-builder.yml` 逐项

```yaml
# electron-builder.yml:7-19（节选）
appId: com.llama.launcher
productName: llama-launcher
directories:
  output: dist
  buildResources: build
# 只打这三样：主进程、preload、渲染层
files:
  - out/**/*
  - package.json
  - "!**/*.map"
```

- `appId`：应用唯一标识（Windows 上主要影响开始菜单/卸载项的身份识别）。
- `directories.output: dist`：产物落点，但运行时会被覆盖 —— 脚本会追加
  `--config.directories.output=<选定目录>`（`scripts/package.mjs:476`）。
- `files`：**只有 `out/` 三份产物 + `package.json`**，没有 `src/`、没有 `node_modules/`、
  没有 llama.cpp、没有模型 —— 它们几十 GB，而且用户本来就会换构建版本
  （`electron-builder.yml:4-5`）。`"!**/*.map"` 排除 source map。
- `directories.buildResources: build` 是 `icon: build/icon.ico` 的来源目录。

`electronDist: .electron-dist`（`electron-builder.yml:34`）的第一层作用是**绕开另一条坏路径**
（`electron-builder.yml:24-29`）：electron-builder 26.x 的 `resolveCacheMode` 去读
`@electron/get` 的 `ElectronDownloadCacheMode`，但依赖范围写的是 `^3.0.0` 而 3.0.0 不导出该符号，
于是打包挂在 `TypeError: Cannot read properties of undefined (reading 'ReadWrite')`。
指定 `electronDist` 后那条"下载并解压 Electron zip"的路径根本不会被走到；
第二层作用（跳过 `default_app.asar`）见 3.8。而 `asar: false`（`electron-builder.yml:55`）
的收益写在注释里："明文目录顺带也更好排查：出问题可以直接进 `resources/app/` 看产物。"

图标也是踩坑后的选择（`electron-builder.yml:57-61`）：直接给现成的 `.ico`，
不让 electron-builder 从 PNG 转换，因为它的转换要调 app-builder 的二进制、在本机报错。
我用只读方式核对了这个"手写 ICO"，它确实是"ICO 头 + 内嵌 256×256 PNG"：

```text
build/icon.ico 共 8066 字节，前 22 字节：
00 00 | 01 00 | 01 00    ← 保留 0 / 类型 1(ICO) / 条目数 1
00 00 00 00              ← 宽 0、高 0（0 = 256）、调色板 0、保留 0
01 00 | 20 00            ← 平面数 1、位深 0x20 = 32 bpp
6C 1F 00 00              ← 数据大小 0x1F6C = 8044
16 00 00 00              ← 数据偏移 0x16 = 22
offset 22 处：89 50 4E 47 0D 0A 1A 0A   ← PNG 签名
```

（`build/icon.png` 是 8044 字节，正好等于上面那个"数据大小"。）

两个目标是 `portable` 与 `nsis`（`electron-builder.yml:62-78`），产物名分别是
`llama-launcher-${version}-portable.exe` 与 `llama-launcher-${version}-setup.exe`
（`${version}` 来自 `package.json:3` 的 `0.2.0`）。
**`portable`** 整包一个 exe、双击即用，是 3.10 那个 bug 的主角；
**`nsis`** 的 `oneClick: false` = 有向导、`perMachine: false` = 只给当前用户装、
`allowToChangeInstallationDirectory: true` = 安装路径可改 ——
注意"路径可改"意味着**可能装进只读目录**，这正是 `chooseDataLayout` 第三条分支存在的原因。

### 3.8【打包】`.asar` 坑的完整因果链

把 `scripts/package.mjs:7-23` 与 `electron-builder.yml:38-48` 两份记录拼起来：

```text
1. electronDist 指向已解压目录 → 走 "custom unpacked Electron distribution" 分支：
     emptyDir(appOutDir) → copyDir(发行目录 → 产物) → return false
2. copyDir 是全量复制 → Electron 自带的 resources/default_app.asar 一起进了产物
3. return false → isFullCleanup = false
     → cleanupAfterUnpack() 里 unlinkIfExists(产物里的 default_app.asar) 被整个跳过
     → 那个 asar 永远留在产物里（不是"删失败"，是压根不删）
4. 本机常驻进程（火绒 / Everything / Windows 搜索）解析它并长期持有句柄：能读、不能改名、不能删除
5. 下一次打包开头 emptyDir(appOutDir) 必须删掉它，而那一步不吞错误
     → EBUSY: resource busy or locked, unlink '...\resources\default_app.asar' → 整个打包中断
```

实测数据（`electron-builder.yml:46-48`）："两个废弃输出目录里残留的 4 个 `.asar`
全部长期锁定（可正常读取，但改不了名、删不掉），同目录下新建的普通文件却都能正常删"。
`scripts/package.mjs:21-23` 还补了取证方法：残留的 `.asar` 与"内容仿造的普通 `.asar` 文件"
行为不同 —— 说明占用者是在**解析**真正的归档。

**对策①：让产物里根本不出现 `.asar`。** 跳过的文件是一个常量
（`scripts/package.mjs:81-82`），镜像实现的核心就一处（`scripts/package.mjs:318-324`）：
`fs.linkSync(from, to)` 成功就 `stats.linked += 1`，失败（跨卷等极端情况）则退化为 `fs.copyFileSync`。

```js
// scripts/package.mjs:81-82
/** 镜像里要跳过的文件（相对发行目录），也就是本次问题的元凶。 */
const SKIPPED_IN_MIRROR = [path.join("resources", "default_app.asar")];
```

**对策②：清理失败就换目录，而不是让整个打包失败。** 清理函数不用
`fs.rmSync(dir, {recursive:true})`：那样一遇 `EBUSY` 就整体抛错，
且不会告诉我们是哪几个文件被占用（`scripts/package.mjs:209-211`）。

```js
// scripts/package.mjs:386-392
  const first = removeTree(path.join(preferred, APP_OUT_NAME));
  if (first.blocked.length === 0) return { dir: preferred, fallback: false, blocked: [], removed: first.removed };

  const stamp = new Date().toISOString().replace(/[-:T]/g, "").slice(0, 14);
  const alternate = `${preferred}-fallback-${stamp}`;
  const second = removeTree(path.join(alternate, APP_OUT_NAME));
  return { dir: alternate, fallback: true, blocked: first.blocked, removed: first.removed + second.removed };
```

`APP_OUT_NAME` 就是 `"win-unpacked"`（`scripts/package.mjs:73`）—— **只有它需要预清理**，
因为 electron-builder 的 `emptyDir` 只清这个目录。选定目录后被拼进命令行（声明式覆盖，
所以即使退到 `dist-fallback-<时间戳>/`，`electron-builder.yml` 也不用改）：
`--config.directories.output=${picked.dir}`（`scripts/package.mjs:474-478`）。

### 3.9【打包】`package.mjs` 的其余几件小事

**（1）输出目录里"跑过才有的文件"先保下来**（便携版把配置放在 exe 旁边，
而打包前会清空 `win-unpacked`，等于把用户的配置一起删了）：`RUNTIME_FILES =
["llama-launcher.json", path.join("data", "llama-launcher-settings.json")]`
（`scripts/package.mjs:102`）。流程：清理前 `snapshotRuntimeFiles` 读进内存
（`scripts/package.mjs:454`）、构建成功后 `restoreRuntimeFiles` 放回
（`scripts/package.mjs:485`），且**已存在的不覆盖**（`scripts/package.mjs:136-139`）。

**（2）顺带清掉上一次的安装包**（只删自己的前缀，避免误删目录里的其它东西）：
`ARTIFACT_PREFIX = "llama-launcher-"`（`scripts/package.mjs:87-88`）。

**（3）镜像带版本标记**（`.llama-mirror-source`，`scripts/package.mjs:84-85`）：
`ensureElectronDistMirror()` 把 `node_modules/electron/package.json` 的 `version` 写进标记，
一致就直接复用（`scripts/package.mjs:340-348`）。本机现存标记内容是 `44.3.0`。

**（4）`--check` 只做诊断**：`const checkOnly = argv.includes("--check")`
（`scripts/package.mjs:424-426`），命中就打印"✔ 诊断结束"并 `return 0`
（`scripts/package.mjs:463-466`）。我写这章时实测跑过一次：

```text
  · 复用 .electron-dist（Electron 44.3.0）
  · 发现上次运行留下的 llama-launcher.json，构建后会原样放回
  · 已清理 dist\win-unpacked（删除 170 项）
✔ 诊断结束：本次会输出到 E:\Code\llama\llama-launcher\dist
```

**注意一个反直觉的地方**：`--check` 虽然不调 electron-builder，但它执行在 `checkOnly` 判断
**之前**就已经调了 `prepareOutputDir`（`scripts/package.mjs:459`，判断在 `463`），
所以那次运行真的删掉了 `dist\win-unpacked\` 里的 170 项。
把 `--check` 当"绝对只读"是误解 —— 它的准确含义是"只诊断、不编译不打包"。

### 3.10【打包】便携版路径解析：一个用户可见的 bug

```ts
// src/main/paths.ts:36-41（节选）
 * 为什么需要这一步：**单文件便携版（`portable` 目标）每次启动都会先把自己解压到
 * `%TEMP%\<随机名>\`**，所以 `app.getPath("exe")` 指向的是那个临时目录。
 * 直接拿它当应用目录的话，配置与数据都会写进临时目录，而下次启动解压出来的目录名又不一样 ——
 * 用户看到的现象就是「便携版每次启动配置都被重置」（实测确认过）。
 * electron-builder 的 `portable.nsi` 为此注入了 `PORTABLE_EXECUTABLE_DIR`（= 便携 exe 所在目录），
 * 有它就以它为准。`--dir` 免安装目录、NSIS 安装版和开发模式都不会有这个变量，走 exe 目录。
```

修法就是一个优先取环境变量的小函数（`src/main/paths.ts:46-56`）：先
`const portable = input.portableExecutableDir?.trim()`，有值就 `return resolve(portable)`
（`resolve` 归一化尾部分隔符与正斜杠；非法路径静默退回，注释写着
"宁可落到临时目录，也不能因此起不来"），没值才 `return dirname(input.exePath)`。
边界情况全被测试钉住：空串/纯空白退回 exe 目录（`src/test/paths.test.ts:96-100`）、
尾部分隔符或正斜杠要归一化（`src/test/paths.test.ts:102-106`）。

拿到"应用目录"后，落点由 `chooseDataLayout` 决策（三条分支见 `src/main/paths.ts:127-159`），
并在主进程里**早于 app ready** 应用：`layout.portable` 为真时
`app.setPath("userData", layout.dataDir)`（`src/main/index.ts:76-86`）。
注意 `defaultUserDataDir` 传的是**函数**：`app.getPath("userData")` 一调用就会把
`%APPDATA%\<应用名>` 建出来（`src/main/index.ts:72-74`），惰性求值才能让它彻底不出现。

### 3.11【打包】时间戳统一：`touchTree`

```js
// scripts/package.mjs:150-156（节选）
 * 为什么需要它：产物里 Electron 自带的那些文件（`electron.exe`、`*.dll`、`*.pak`、`locales/`）
 * 时间戳是 **1980-01-01**，看着很怪。原因在源头：Electron 官方 zip 的中央目录把全部 75 个条目
 * 的时间字段都写成 MS-DOS 时间的最小值（`dosDate=0x0021 dosTime=0x0000` = 1980-01-01 00:00:00，
 * 按 UTC 解释、在 UTC+8 显示成 08:00）—— 这是可复现构建的常规做法，让同一版本的 zip 字节恒定。
 * 解压、硬链接镜像、electron-builder 复制都会**保留 mtime**，于是 1980 一路传到产物里。
```

⚠ **这段注释的结论已经过期，别照着它理解现在的行为** —— 它说开关"默认关闭"，
但现在的实际逻辑是**默认开**：`const touch = !argv.includes("--no-touch") &&
process.env["LLAMA_PACKAGE_TOUCH"] !== "0"`（`scripts/package.mjs:434`）。

| 想干什么 | 怎么写 |
| --- | --- |
| 默认（统一成构建时间） | `pnpm package` |
| 保留原始时间戳 | `pnpm package:keep-time`（= `--win --dir --no-touch`，`package.json:19`） |
| 同上，用环境变量 | `$env:LLAMA_PACKAGE_TOUCH='0'; pnpm package` |
| 换输出目录到工作区之外 | `$env:LLAMA_PACKAGE_OUT='E:\llama-launcher-dist'`（`scripts/package.mjs:53`、`451`） |

`touchTree` 的遍历顺序有个细节（`scripts/package.mjs:178`）：
"先动文件再动目录：这样目录的 mtime 是'最后一次内容变更'的语义"。
统计里单独记 `failed`（对应正被占用的文件），时间戳改不动**不阻断打包**
（`scripts/package.mjs:501-504`）。

### 3.12【打包】怎么验证产物

脚本实际认的开关（`main()` 里手写判断）：`--check`（`scripts/package.mjs:426`）、
`--no-touch`（`scripts/package.mjs:434`）；`--touch` 会被从透传参数里剔除但**没有任何代码读它**
（`scripts/package.mjs:435` —— 因为默认就统一时间戳了）；`--win` / `--dir` / `portable`
等原样透传给 electron-builder（`package.json:17-20`）。三个验收点：

**一、产物里一个 `.asar` 都没有。**

```powershell
Get-ChildItem -Recurse -Force -Filter *.asar E:\Code\llama\llama-launcher\dist   # 期望：无输出
```

我核对过一次，确实**一条都没有**：`dist/win-unpacked/resources/` 下只有 `app/` 目录，
里面是 `out/` 三份产物 + `package.json`（`asar: false` 的效果）。
对照源目录：`node_modules/electron/dist/resources/` 里只有 `default_app.asar` 一个文件，
而镜像 `.electron-dist/resources/` 是**空的** —— 被跳过的就是全部。

**二、配置与数据要还在。** 打包前会打印"发现上次运行留下的 llama-launcher.json，
构建后会原样放回"，成功后打印"已放回：…（应用下次启动直接用它，不会重新探测）"

**三、日志里能对上关键行。** 正常一次打包会打印 `.electron-dist` 是复用还是重建

若看到 `⚠ 首选输出目录里有文件被其它进程占用，清不掉`，说明走了 fallback ——
脚本会列出占用文件并给两条出路（重启释放句柄 / 加进火绒信任区或在 Everything 关掉内容索引，
`scripts/package.mjs:405-416`）。

## 4. 踩过的坑与设计取舍

### 4.1 「不是删失败，是压根不删」

> 最后的 `false` 让 isFullCleanup=false，于是 `cleanupAfterUnpack()` 里
> `unlinkIfExists(产物/resources/default_app.asar)` **被整个跳过**（不是"删失败"，是压根不删）。
>
> —— `electron-builder.yml:41-42`

启发：**"清理没生效"和"清理被拒绝"是两种不同的故障**。分不清就会去怀疑杀软、怀疑权限，
而真正的原因在上游代码的一个 `return false`（完整链条见 3.8）。

### 4.2 不跟占用者较劲，而是换一条不碰它的路

> 所以对策不是「等它松手」，而是让产物里根本没有 `.asar`：
>   · default_app.asar：`scripts/package.mjs` 生成的 .electron-dist 镜像里把它跳过了
>   · app 本体：本文件保持 asar: false，以 resources/app/ 明文目录形式存在
>
> —— `electron-builder.yml:50-53`

### 4.3 时间戳开关"写了等于没写"

> 早先做成默认关闭（要显式 `LLAMA_PACKAGE_TOUCH=1`），结果是"重建完发现产物里那 71 个文件
> 时间还是 1980"反复出现 —— 开关写了等于没写。
>
> —— `scripts/package.mjs:430-431`

通用原则：**默认值应该选"绝大多数人想要的那个"**，可选项留给少数派（`--no-touch`）。

### 4.4 清理产物 = 删用户的配置

> 实测踩过：把预加载模型、每模型的 ctx / 输出上限都改好之后重建一次，产物里那份配置
> 被清掉、应用重新生成，命令又回到了旧值（`-c 16384 -n 8192`），而项目根目录的配置
> 打包版根本不读。
>
> —— `scripts/package.mjs:96-98`

README 给了更省事的长期做法：把 `win-unpacked` 拷到稳定目录再跑，别直接在 `dist/` 里跑
（那里每次打包都会被重建，`README.md:568-569`）；同时提醒**开发模式与打包版读的是两份不同的
配置**（`README.md:571-573`）。

### 4.5 参数名不等于行为

README 对 `--check` 的描述是"只做打包前诊断"（`README.md:506`），
但如 3.9 实测，它会真的清空 `dist\win-unpacked`。读脚本要看**判断发生在哪一行**，
而不是相信参数的语义名字。

## 6. 自测题

**第 1 题**：`node --test` 在这个项目里跑不起来，具体哪一步失败？现在的做法为什么不需要测试框架？

<details>
<summary>答案</summary>

`node --test` 会**为每个测试文件 spawn 一个子进程并把 stdio 接成管道**，受限环境里这一步
直接 `EPERM`（`src/test/run-tests.ts:4-5`）。

现在 `run-tests.ts` 在**同一个进程**里 `import` 全部测试文件。`node:test` 是 Node 内置模块：
文件被 import 时里面的 `test()` 就注册并执行了，它自己收集结果、打印汇总
（`# tests 192 / # pass 192`）并设置退出码。所以既不需要子进程，也不需要 Jest/Vitest 之类的
框架 —— `package.json:37-52` 里确实没有。

</details>

**第 2 题**：我写了 `src/test/my.test.ts`，有 5 个 `test()`，但 `pnpm test` 还是 192 个。为什么？

<details>
<summary>答案</summary>

因为执行是靠 `run-tests.ts` **显式 import** 触发的，没有目录扫描。必须加进那张清单
（`src/test/run-tests.ts:11-41` 的分组注释下），例如在
`// ---- 纯格式化（渲染层也用的叶子模块）----` 那组里补一行 `import "./my.test.ts";` ——
少这行，5 个测试一个都不会跑。

快速核对：`src/test/` 里 `.test.ts` 的个数应等于 `run-tests.ts` 里 import 的行数（当前都是 18）。

</details>

**第 3 题**：`pnpm typecheck` 过了、`pnpm test` 也过了，能说明代码没问题吗？

<details>
<summary>答案</summary>

不能。两者守不同的东西：`pnpm test` 守**行为正确性**，而且因为类型擦除，**类型错误完全不会
阻止它运行**；`pnpm typecheck` 守**类型正确性**（字段名、可空性、`import type`、
有没有用 `enum` 这种擦除模式不支持的语法 —— `tsconfig.json:13,16`），但它一行都不执行，
`assert` 里的期望值写错了它看不见。所以两个都要跑。

</details>

**第 4 题**：`resources/app.asar` 和 `resources/default_app.asar` 有什么区别？哪个被跳过了、为什么？

<details>
<summary>答案</summary>

`app.asar` 是**我们的应用**本体（`out/` 三份产物 + `package.json`）；`default_app.asar` 是
**Electron 发行包自带**的"没给 app 时启动的空壳应用"。我们永远自带 app，所以后者用不到。

本项目两个都不用 `.asar`：`app` 走 `asar: false`（`electron-builder.yml:55`）变成
`resources/app/` 明文目录；`default_app.asar` 在 `.electron-dist` 镜像里被跳过
（`scripts/package.mjs:81-82`）。

**为什么必须跳过它**：自定义 `electronDist` 时 electron-builder 走
`emptyDir → copyDir → return false`，那个 `return false` 让 `cleanupAfterUnpack()` 里删它的
那两行被整个跳过（`electron-builder.yml:39-42`），于是它每次都会留在产物里；
下一次打包开头的 `emptyDir` 必须删掉它，一旦被常驻进程占用就报
`EBUSY: resource busy or locked, unlink ... default_app.asar` 并中断打包。

</details>

**第 5 题**：单文件便携版为什么不能直接用 `app.getPath("exe")` 的目录当应用目录？
`--dir` 免安装目录会有同样的问题吗？

<details>
<summary>答案</summary>

因为单文件便携版**每次启动都把自己解压到 `%TEMP%\<随机名>\`**，`app.getPath("exe")` 指的就是
那个临时目录。拿它当应用目录的话配置写进临时目录，而下次启动解压出的目录名又不一样 ——
用户看到的现象是"便携版每次启动配置都被重置"（`src/main/paths.ts:36-41`）。
修法是优先取 electron-builder 注入的 `PORTABLE_EXECUTABLE_DIR`，没有它才退回
`dirname(exePath)`（`src/main/paths.ts:46-56`）。

`--dir` 免安装目录**没有**这个问题：它是实实在在解压出来的目录，exe 就在那儿、也不会每次换名字，
本来就该走 `dirname(exePath)` 那条分支。NSIS 安装版同理（这时 `chooseDataLayout` 还会进一步
判断目录是否可写，只读就退回 userData）。

</details>
