## 1. 先看问题

假设你要写一个「一键启动 llama-server」的小工具，最朴素的写法是 `spawn("llama-server.exe", ["-m", model])`
然后打印「已启动」。这段代码会同时踩四个坑：它**闪一个黑色控制台窗口**，看起来像流氓软件；
你**不知道它到底起来没有**（`spawn` 返回只代表进程创建成功，端口可能还没监听）；它可能因为显存不足、
端口被占用、参数名不被这个版本认识而**立刻退出**，用户却只看到「已启动」；你关掉界面后**显存没释放** ——
`kill` 只杀了父进程，它留下的子进程还占着显存，下次启动直接 OOM。

本章的四个主角正好对应这四个坑：`spawn` 的参数（`src/core/llamaProcess.ts:223-228`）、
TCP 轮询 `waitForTcp`（`src/core/health.ts:144-160`）、日志分类与诊断
（`src/core/logLines.ts:164`、`src/core/logLines.ts:314`）、两级停止 + `killTree`（`src/core/llamaProcess.ts:311-342`）。

## 2. 核心概念

### 2.1 两类子进程：探测用 vs 服务用

同样是「跑一个子进程」，本项目里有两种用途完全不同的函数，**混用就出事**：
`runCapture(exe, args, timeoutMs)` 是**跑完就退**的一次性命令，用来问 `--version` / `--help`
（`src/core/llamaProcess.ts:364-368`）；`LlamaServer` 是**长期运行**的服务进程（`:117`）。
错误处理哲学是相反的。`runCapture` **永不抛异常**，命令跑不起来就把原因写进返回值的 `error` 字段
（`396-399`）——「这个 exe 探测不了」是需要展示给用户的**正常结果**，不是程序 bug。
而 `LlamaServer.start()` 只在**调用方用法错误**时抛异常（`214`），
「进程起不来」则返回 `ready: false` + `diagnosis`（`277`）。

### 2.2 进程状态机 `ServerState`

6 个取值定义在 `src/core/llamaProcess.ts:30`：`idle`（还没启动或已停干净，`314`）、
`starting`（`spawn` 调完了，正在等端口，`221`）、`running`（**端口已开始监听**，`261`）、
`stopping`（正在停止，`318`）、`exited`（我们自己停的，`246`）、
`failed`（spawn 失败 / 非预期退出 / 等不到端口，`239`、`248`、`276`）。

关键理解：**`running` 不等于「模型加载好了」**：

```ts
// src/core/llamaProcess.ts:27-28
 * `running` 的含义是**端口已开始监听**，不代表模型已经加载完
 * （router 模式下模型是按需加载的，要另外看 `/health`）。
```

界面上的「运行中」直接显示 `ServerState`（`src/renderer/src/components/StatusBar.tsx:30-32`），
而「服务就绪」是另一个概念 `HealthState`：「服务就绪」对应 `/health` 返回 200，「模型加载中」对应 503，
文案与 tooltip 在 `src/renderer/src/components/StatusBar.tsx:17-18`。所以完全可能「状态是 `running`，
但健康状态是 `loading`」。

### 2.3 行缓冲：为什么不能直接 `chunk.toString()`

`spawn` 的 `stdout` 事件给你的是**块**，块边界和行边界没关系：一行日志很可能被切成两块。
不做缓冲，界面上就随机出现半行，按行做的关键字判断也会漏（`src/core/logLines.ts:4-6`）。
`LineSplitter`（`src/core/logLines.ts:18`）就是解决它的：`push(chunk)` 只吐**已经完整**的行，
最后一段没换行的留在内部缓冲，等下一块或 `flush()`（`src/core/logLines.ts:33-50`、`60-65`）。

### 2.4 就绪的两套判断：TCP 与 `/health`

**TCP 能不能连上**（`probeTcp`，`src/core/health.ts:50`）判断「进程起来没有」，是 `start()` 等待的目标
（`src/core/llamaProcess.ts:252-257`）；**`/health` 的 HTTP 状态码**（`fetchHealth`，`src/core/health.ts:94`）
判断「服务可用到什么程度」—— 200 → `ready`，503 → `loading`（正常中间态），其它 → `error`，
连不上 → `unreachable`（`src/core/health.ts:23`）。为什么不能用 `/health` 判断「起来没有」？
因为 router 模式下模型没加载时 `/health` 返回 **503**，把它当失败就会
「服务其实已经好了，但界面永远打不开网页」（`src/core/health.ts:5-10`）。

### 2.5 指标的三层结构：样本 / 历史 / 分列序列

`MetricsSample`（`src/core/metrics.ts:29`）是**某一时刻的一张整机快照**；采样器用一个数组 `ring` 存历史，
超过上限裁掉最旧的（`src/core/metrics.ts:215-218`）；`MetricsSeries`（`src/core/metrics.ts:50`）
把历史**摊成「一列一个指标」**交给渲染层画折线。为什么要多这一层？
画图需要的是「同一个指标的连续值」，不是「每个时刻的一整包数据」。分列之后 `series.vramUsedMiB[i]`
与 `series.at[i]` 一一对应，渲染层**按下标画线**就行，不必遍历样本（测试明确断言所有序列等长，
`src/test/metrics.test.ts:51-54`）；而 `null` 被统一定义为「当时测不到」，所以画线时要**断开**
（`src/renderer/src/components/MetricsPanel.tsx:16-18`）。

### 2.6 可注入的采集函数

`MetricsSampler` 的构造参数里有一个 `collectGpus`（`src/core/metrics.ts:112`），默认走真的 `nvidia-smi`
（`src/core/metrics.ts:147`）。单测把它换成假实现，于是「没装显卡的开发机」也能把采样逻辑测干净
（`src/test/metrics.test.ts:57-75`）。这个手法本章会反复出现：**把副作用变成一个可替换的参数**。

## 3. 代码怎么走

### 3.1 `runCapture`：一次性命令，永不抛异常

返回值里的 `error` **只在超时或无法执行时存在**（`src/core/llamaProcess.ts:358-368`）。核心是三个事件的
竞争处理，`finish` 里用 `settled` 标志：置位后直接 `return`，保证只 `resolve` 一次
（`src/core/llamaProcess.ts:375-379`）。超时后还会收到一次 `exit`，`error` 与 `exit` 也可能都到 ——
没有这个标志，返回的 `code` / `error` 就取决于事件顺序，明明是超时却可能变成「退出码 0，无错误」。
`probeTcp` 用了同样手法（`src/core/health.ts:53-59`）。

`stdout` 与 `stderr` **分开收集**（`src/core/llamaProcess.ts:390-395`）再由调用方拼接：`probeServer`
就是直接相加（`src/core/launcher.ts:54-55`），原因是**llama.cpp 的版本横幅历史上走过 stderr，
只读 stdout 会拿到空字符串**（`42-43`）。`runCapture` 全项目出现在三处：`--version` / `--help`
（`52-53`）、查 GPU（`src/core/gpu.ts:166`）、查驱动版本（`src/core/precheck.ts:628`）。

### 3.2 `LlamaServer.start()`：spawn 的四个参数

```ts
// src/core/llamaProcess.ts:223-228
    const child = spawn(opts.exe, opts.argv, {
      cwd: opts.cwd ?? dirname(opts.exe),
      windowsHide: true,
      stdio: ["ignore", "pipe", "pipe"],
      env: { ...process.env, ...(opts.env ?? {}) },
    });
```

`cwd` 默认取 **exe 所在目录**：llama.cpp 的 DLL 就在 exe 旁边，换个目录会起不来（`src/core/llamaProcess.ts:44`）；
`windowsHide` 不闪黑色控制台窗口（`:7`）；`stdio` 的 stdin 不要、stdout 与 stderr 都要接管道才拿得到日志（`:8`）；
`env` 用展开合并 —— **追加覆盖而不是替换**，否则子进程会丢掉 `PATH` 这类必需变量（`201-202`）。

在 `spawn` 之前会把 `splitter` / `lines` / `exitInfo` / `spawnError` 全部重置（`src/core/llamaProcess.ts:216-221`），
上一次启动的残留不会污染这一次的诊断。`start()` 还有一道防御：

```ts
// src/core/llamaProcess.ts:214
    if (this.child !== null) throw new Error("已有 llama-server 进程在运行，请先调用 stop()");
```

抛错而不是返回 `ready: false`，是因为那是**调用方的用法错误**，和「进程起不来」是两回事。

### 3.3 日志泵与退出判定

`pump` 把每一块输出喂给行缓冲再逐行交给 `handleLine`（`src/core/llamaProcess.ts:231-232`），
`stdout` 与 `stderr` 都走它，因此**两个流共用同一条分类逻辑**（`234-235`）。`handleLine` 做三件事：
分类 → 存环形缓冲 → 透传回调（`184-190`），缓冲按 `maxLogLines`（默认 2000）裁剪，目的是
**失败诊断有素材可用、同时别把内存吃光**（`180-182`）。

退出事件是本章最实用的一个分支 —— **区分「我停的」和「它自己崩的」**：

```ts
// src/core/llamaProcess.ts:242-249
    child.on("exit", (code, signal) => {
      for (const line of this.splitter.flush()) this.handleLine(line);
      this.exitInfo = { code, signal };
      if (this.state === "stopping") {
        this.setState("exited", "已停止");
      } else {
        this.setState("failed", `进程退出（code=${code}${signal ? `, signal=${signal}` : ""}）`);
```

两个细节：退出前先 `flush()` 把最后一段没有换行的残留吐出来，否则最后一行日志会丢（`src/core/logLines.ts:52-56`）；
退出是预期还是意外，靠 `state === "stopping"` 这个**上下文**判断，而不是猜退出码。

### 3.4 等待端口：`hasExited` 为什么必须传

```ts
// src/core/llamaProcess.ts:252-257
    const wait = await waitForTcp({
      host: opts.host,
      port: opts.port,
      timeoutMs: opts.readyTimeoutMs ?? 90_000,
      hasExited: () => this.hasExited(),
    });
```

`waitForTcp` 的循环**每轮先看进程退出、再看端口**（`src/core/health.ts:149-155`）：
`hasExited()` 为真就返回 `reason: "exited"`，`probeTcp` 成功就返回 `ok: true` 与等待时长。
如果不传 `hasExited`，一个「参数写错、启动即崩」的进程会让界面白等整整 90 秒。单次探测超时取
`min(intervalMs, 800)`，避免探测本身比轮询间隔还久（`136-137`）。

等待成功就进 `running` 并返回 `ready: true`（`src/core/llamaProcess.ts:259-263`）；失败则按三种情况给不同的话，
并在已收集的日志上跑一次诊断（`265-277`）：spawn 失败说 spawn 的原因、进程先退出说退出码、等满超时说等了多久，
最后 `setState("failed", note)` 并把 `diagnosis` 一起返回。这里用到的 `spawnFailure()` / `exitState()`
存在的原因写在 `149-152`：TS 的控制流分析认死这两个字段恒为 `null`，用方法取一次才能绕开误判。

### 3.5 停止：两级终止与「尽力而为」的 `killTree`

先 `child.kill()`（`src/core/llamaProcess.ts:329`，`graceMs` 默认 5000 见 `311`），
再用 `Promise.race` 等它退出；超时才动用第二级 `await killTree(pid)` 并再等最多 3 秒（`334-338`）。
Windows 上 `kill()` 是硬终止、没有 SIGINT 可发，但多数情况已经够用；只有它卡住（正在写大文件、
驱动层未响应）时才需要兜底（`299-301`）。`killTree` 的全部实现就是起一个 `taskkill`：

```ts
// src/core/llamaProcess.ts:96-99
    const killer = spawn("taskkill", ["/PID", String(pid), "/T", "/F"], {
      windowsHide: true,
      stdio: "ignore",
    });
```

`/T` 是「连整棵进程树」，`/F` 是强制。**为什么必须兜底**，注释给了真实后果：

```ts
// src/core/llamaProcess.ts:84-86
 * 为什么需要：llama-server 被 kill 后若有残留子进程，它会继续占着显存，
 * 表现为"关掉界面后显存莫名没释放、下次启动就 OOM"。
 * 因此 `stop()` 在优雅终止超时后用它兜底。
```

`killTree` **永不抛异常**，因为这一步是「尽力而为」：`taskkill` 不存在或失败也不能让停止流程崩掉
（`src/core/llamaProcess.ts:88-89`），所以它把 `exit` 与 `error` 都接了 `resolve`（`100-101`）。
`stop()` 自己也幂等：没有进程时直接置 `idle` 返回，不抛异常（`312-316`）。

### 3.6 `logLines.ts`：一行日志变成什么

`LineSplitter.push`（`src/core/logLines.ts:33-50`）的边界处理：兼容 `\r\n` 与 `\n`、返回的行不带 `\r`、
结尾没换行的留在缓冲里；另外有一条兜底 —— 缓冲涨到 100 万字符还没有换行就直接当一行吐出，防内存被吃光
（`44-48`，单测在 `src/test/logLines.test.ts:20-27`）。`classify(line)` 返回的 `LogEvent` 有 5 个字段：
`kind`（10 种大类，`87-97`）、`level`、`message`、`metrics`、`raw`（`112-120`）。
`level` **优先用结构化等级字母**而不是猜关键词（`175-178`），前缀正则 `RE_LEVEL_PREFIX` 在 `141`，
匹配 `0.00.146.987 W srv ...` 里的那个字母。为什么需要它？因为 b10488 的日志已经是这种结构化格式，
而 `CORS is set to allow all origins` 这类告警**不含 warn 字样**，只能靠等级字母识别
（`133-139`，测试在 `src/test/logLines.test.ts:56-60`）。另外 `kind` 的判定顺序就是优先级，注释特别强调
错误 / 告警必须排在 `model-loading` 之前，否则 `llama_model_loader: warning: ...` 会被吞进「模型加载中」
这一桶里（`src/core/logLines.ts:192-200`）。

`LogMetrics` 从日志里顺带抽 4 个数字（`src/core/logLines.ts:100-109`，抽取在 `165-173`）：
prompt 处理速度、生成速度、实际生效的 `n_ctx`、offload 的层数。口径是**抽不到就是 `undefined`，不代表 0**。

### 3.7 `seq` 与 `at`：为什么要额外造这两个字段

llama.cpp 自己那串时间戳是**进程内的累计时间**，不是墙上时钟；而「内容完全相同的两行日志」
在 React 列表里会被折叠掉。主进程的 `toLogPush` 因此补了两个字段 —— `seq` 做 React key 与去重、
`at` 取当前时间戳（原文见 `src/main/payload.ts:197-199`，实现是 `207-209`）。`seq` 由会话持有并自增
（`src/main/session.ts:606-607`），渲染层拿它当 key（`src/renderer/src/components/LogPane.tsx:97`）、
用 `at` 显示时钟（`98`）。

```ts
// src/main/payload.ts:198-200
 * `seq` 是自增序号：渲染层用它做 React key 与去重（避免"内容相同的两行"被折叠掉）。
 * `at` 取当前时间戳，因为 llama.cpp 自己那串时间戳是进程内的累计时间，不是墙上时钟。
```

实现就是把它们透传进 `LogPush`（`src/main/payload.ts:207-209`）。

### 3.8 日志流到界面：一条完整的推送链路

会话的 `onLine` 回调做四件事（`src/main/session.ts:605-615`）：自增 `seq` 并转成 `LogPush`、
推进内存缓冲（上限 `LOG_BUFFER_LIMIT = 4000`，`src/main/session.ts:66`）、推给界面、顺手把吞吐喂给采样器；
`onState` 则同步服务状态给采样器并推送（`616-619`）。主进程把这三个回调接到窗口上 —— `onLog` / `onState` /
`onMetrics` 分别 `send` 到 `IPC.pushLog` / `IPC.pushState` / `IPC.pushMetrics`，其中 `onState` 里还顺手让
托盘图标跟着变色（`src/main/index.ts:118-124`）。渲染层订阅后只做追加
（`src/renderer/src/hooks/useLauncher.ts:285-291`），界面刚打开时的历史日志来自主进程缓存
（`IPC.logsRecent`，`src/shared/ipc.ts:46-47`；`src/main/session.ts:724-726`），卸载时**务必关掉指标采样**：
「否则会一直每秒钟起一个 nvidia-smi 进程」（`src/renderer/src/hooks/useLauncher.ts:303-304`）。

### 3.9 就绪探测：用 HTTP 查「可用程度」

```ts
// src/core/health.ts:98-104
    if (res.status === 200) return { state: "ready", httpStatus: res.status, body };
    // 503 = router 模式还没加载模型，不是故障
    if (res.status === 503) return { state: "loading", httpStatus: res.status, body };
    return { state: "error", httpStatus: res.status, body, detail: `HTTP ${res.status}` };
  } catch (err) {
    return { state: "unreachable", detail: err instanceof Error ? err.message : String(err) };
  }
```

三个边界：200 → `ready`；503 → `loading`；**其它任何状态码** → `error`；抛异常（连接被拒 / 超时 /
DNS 失败）→ `unreachable` 并把原始错误消息放进 `detail`。正文读取失败不影响状态判断（`.catch(() => "")`，
`src/core/health.ts:97`）。`0.0.0.0` / `::` 这种「监听所有网卡」的地址必须换回 `127.0.0.1` 才能请求（`77-81`），
`LlamaServer.health()` 做了同样替换（`src/core/llamaProcess.ts:290-293`）。

**轮询是渲染层驱动的**：进程在跑时每 2 秒查一次状态（`STATUS_POLL_MS = 2000`，
`src/renderer/src/hooks/useLauncher.ts:30`、`341-347`），主进程侧 `status()` 只在真的在跑时才请求 `/health`，
否则 `health` 为 `null`、界面不显示徽标（`src/main/session.ts:686-697`）。会话给 `/health` 的超时是 1500ms，
比别处短，因为「界面每 2 秒轮询一次状态，健康检查不该把轮询节奏拖长」（`668-669`）。

### 3.10 失败诊断：把日志翻成人话

`diagnose(lines)` 按规则表的**声明顺序**匹配，先命中先返回（`src/core/logLines.ts:314-321`）。顺序即优先级，
最典型的是显存不足要排在端口占用之前（`302-309`）：两者都会刷出 `error` 字样，但**给出错误建议比不给建议更糟**。
规则表一共 7 条，每条给出 `code` + `summary` + 若干 `suggestions`（`235-299`），`code` 依次是 `vram-oom`、
`port-in-use`、`preset-parse`、`option-unsupported`、`no-models`、`model-load-failed`、`draft-model`。
它跨到界面时经过 `buildStartReport`（`src/main/payload.ts:220-243`），载荷类型是 `StartReportPayload`
（`src/shared/ipc.ts:213-220`），其中诊断字段的类型叫 `DiagnosisPayload`（`207-211`）。注意它对 `suggestions`
做了浅拷贝，理由是「避免界面侧对数组的改动污染 core 里那份诊断规则表（规则表是模块级常量，会被复用）」
（`src/main/payload.ts:214-216`）。界面上「启动失败就自动切到日志页」也真实存在（`src/renderer/src/App.tsx:29-31`）。

### 3.11 `gpu.ts`：调 `nvidia-smi` 并解析

为什么不用 NVML 绑定：**零依赖、跨驱动版本稳定，输出格式十几年没变**（`src/core/gpu.ts:4-6`）。
代价是每次采集要起一个进程，所以采样间隔取 1 秒。查询参数由字段表拼出（`82-84`），字段表 11 项、
`name` 在最前（`26-38`）。解析是**按位置取值**的（`--format=csv,noheader` 没有表头），所以有一条硬约束：
「改这里必须同步改 `parseNvidiaSmiCsv` 里的取值顺序……位置错一位就会张冠李戴」（`23-24`）。
字段容错收敛到一个函数：`N/A` / `[N/A]` / 空串 / 带单位（`1007 MiB`、`4 %`）都处理，
**解析不出返回 `null` 而不是 0**，因为「0」和「测不到」是两回事（`97-104`）；显卡名真含逗号时
按「字段数 - 10」把名字拼回来，避免后面所有数值整体错位（`131-135`）。

### 3.12 降级路径：没有 NVIDIA 卡也能用

`queryGpus`（`src/core/gpu.ts:166-176`）有两条失败出口，**形状完全相同**：命令跑不起来（`error` 有值，
没装 `nvidia-smi` 或非 NVIDIA 机器）、解析出 0 条记录（按退出码区分「没有返回任何显卡信息」
还是「退出码 N」），都返回 `{ ok: false, gpus: [], error }`。这是「没有 GPU 也能用启动器」的前提（`159-161`）。
采样器接过结果时**只记录原因，不中断循环**（`src/core/metrics.ts:196-198`），界面据此区分「没显卡」与「0%」，
提示文案明确写了「非 NVIDIA 显卡或没装 nvidia-smi 都会这样，不影响 llama.cpp 用纯 CPU 或其它后端跑」
（`src/renderer/src/components/MetricsPanel.tsx:170-172`）。

### 3.13 采样器：开、停与分列序列

`start()` 只做两件事：立刻先采一次（否则界面打开监控页会先空 1 秒），然后挂上定时器；
`stop()` 清掉定时器但**保留历史与最近吞吐**（`src/core/metrics.ts:165-178`），两个方法都幂等
（`src/test/metrics.test.ts:140-156`）。**什么时候开、什么时候停**：界面切到「监控」页时开、离开时关 ——
触发点在面板自己的 `useEffect` 里（`src/renderer/src/components/MetricsPanel.tsx:145-148`），
`watchMetrics` 打开时顺手拉一次快照（`src/renderer/src/hooks/useLauncher.ts:577-586`）。
IPC 通道是 `metrics:watch`（`src/shared/ipc.ts:50-51`），主进程只认 `active === true` 才开
（`src/main/index.ts:509-511`），会话侧就是一行 `start` / `stop`（`src/main/session.ts:871-876`）。

采样一次的内部逻辑：取 CPU 时间片快照做差分 → 等 GPU 采集 → 组装样本 → 推进历史并回调。
「主卡」取 `gpus[mainGpuIndex] ?? gpus[0] ?? null`（序号来自配置的 `main_gpu`，
`src/main/session.ts:825-830`、`846-851`），历史超上限时从头部裁掉（`src/core/metrics.ts:203`、`215-218`）。
`usagePct` 第一次采样必然是 `null`，因为没上一次的快照可比（`src/core/sysinfo.ts:26-27`；
单测 `src/test/metrics.test.ts:77-81`）。**非重入保护**：上一轮还没回来就返回上一轮结果，
避免 `nvidia-smi` 卡顿时进程堆积（`src/core/metrics.ts:188-190`）。

`toSeries` 就是一次纯映射（`src/core/metrics.ts:85-96`），列名与渲染层的 `StatCard` 一一对应
（例如 `series={series.vramUsedMiB}`，`src/renderer/src/components/MetricsPanel.tsx:187-194`）。
**吞吐从哪来**：llama-server 不会主动告诉你 tok/s，它是从日志里抽的 —— 会话在收到含 tok/s 的日志行时
喂给采样器（`src/main/session.ts:613-614`），采样器只在真有数字时才更新（`src/core/metrics.ts:227-234`，
单测 `src/test/metrics.test.ts:110-120`）。

## 4. 踩过的坑与设计取舍

> **坑 1：块边界会把一行切成两半。**「`child_process` 的 stdout 按块给，块边界会把一行切成两半。
> 不缓冲，日志面板里会随机出现半行。」（`src/core/logLines.ts:5-6`）

> **坑 2：把 `/health` 的 503 当失败。**「router 模式下模型还没加载时，`/health` 会返回 **503**。
> 把 503 当失败 → 浏览器永远打不开。」（`src/core/health.ts:5-6`）所以判断「能不能开网页」用 TCP 连通性。

> **坑 3：`--version` 的输出可能走 stderr。**「llama.cpp 的版本横幅历史上走过 stderr，只读 stdout
> 会拿到空字符串」（`src/core/llamaProcess.ts:354-356`）。这是 `runCapture` 坚持把两个流分开返回的原因。

> **坑 4：关键词猜等级会漏。**「有这个前缀时等级以它为准，比关键词猜测可靠
> （"security risk" 这类不含 warn 字样的告警就靠它）」（`src/core/logLines.ts:138-139`）。

> **坑 5：诊断规则的顺序错了比没有诊断更糟。**「显存不足和端口占用都能刷出 "error" 字样，必须先匹配它们」
> （`src/core/logLines.ts:233`）；反过来「给出错误建议比不给建议更糟」（`:306`）—— 识别不出就返回 `null`。

> **坑 6：每秒一个 `nvidia-smi` 是实打实的开销。**「实测 300ms 那种频率会把 CPU 占用明显抬起来，
> 得不偿失」（`src/core/gpu.ts:5-6`）。于是默认间隔 1 秒（`src/core/metrics.ts:103`）、只在监控页开着时采样。

> **取舍：`gpu.ts` 为什么把 `format.ts` 的函数再导出一次。**「渲染层要用这些函数时请直接从
> `core/format.ts` 引用，别经过本文件 —— 本文件为了采集而 import 了 `node:child_process`，会污染浏览器产物。」
> （`src/core/gpu.ts:15-17`）

## 6. 自测题

**第 1 题**：`ServerState` 的 `running` 和界面上的「服务就绪」是同一件事吗？

<details>
<summary>第 1 题答案</summary>

不是。`running` 的含义是**端口已开始监听**（`src/core/llamaProcess.ts:27-28`），`waitForTcp` 成功后置入（`259-262`）。
「服务就绪」是 `HealthState` 里的 `ready`（`/health` 返回 200，`src/core/health.ts:98`），由 `StatusBar` 的
`HEALTH_LABEL` 渲染（`src/renderer/src/components/StatusBar.tsx:14-21`）。所以完全可能出现「状态 `running`，
但健康状态 `loading`（503，模型还没加载完）」。

</details>

**第 2 题**：`runCapture` 里 `settled` 这个标志挡住了什么？去掉会怎样？

<details>
<summary>第 2 题答案</summary>

它保证只结算一次（`src/core/llamaProcess.ts:375-379`）。超时、`error`、`exit` 三个事件可能竞争：超时先
`finish({ code: null, error })` 并 `kill()`，随后子进程真的退出又触发 `exit`。没有它，返回值的
`code` / `error` 就取决于事件顺序 —— 明明是超时，却可能变成「退出码 0，无错误」。`probeTcp` 里有同样的
手法（`src/core/health.ts:53-59`）。

</details>

**第 3 题**：为什么 `stop()` 不能只调 `child.kill()`？

<details>
<summary>第 3 题答案</summary>

Windows 上 `child.kill()` 只终止那一个进程，且是硬终止。如果 llama-server 留下了子进程，
它们会继续占着显存，表现为「关掉界面后显存莫名没释放、下次启动就 OOM」（`src/core/llamaProcess.ts:83-85`）。
所以 `stop()` 先给 5 秒优雅终止窗口，超时后用 `taskkill /PID <pid> /T /F` 杀整棵树（`334-338`、`96-99`）。
`/T` 是关键：没有它就只杀那一个 PID。

</details>

**第 4 题**：`toSeries` 为什么不能省掉，直接把 `MetricsSample[]` 交给渲染层画图？

<details>
<summary>第 4 题答案</summary>

省掉的话每个绘图组件都要自己遍历样本、自己处理「字段可能是 `null`」「有效点不足 2 个」这些情况。
`toSeries` 一次性把历史摊成**等长的列**（`src/core/metrics.ts:50-63`、`85-96`），渲染层直接
`series.vramUsedMiB[i]` 取第 `i` 个点；`null` 的含义被统一定义为「当时测不到」，画线要断开
（`src/renderer/src/components/MetricsPanel.tsx:16-18`）。测试还断言所有列等长，防止某列漏 push
导致曲线错位（`src/test/metrics.test.ts:51-54`）。

</details>

**第 5 题**：一台没装 NVIDIA 卡的机器上，打开「监控」页会发生什么？

<details>
<summary>第 5 题答案</summary>

`queryGpus` 调 `nvidia-smi` 失败，返回 `{ ok: false, gpus: [], error: ... }`（`src/core/gpu.ts:167`）；
采样器把原因记进 `lastGpuError`、`gpus` 为空、主卡为 `null`（`src/core/metrics.ts:197`、`203`），
但 CPU 与内存照常采集（`204-210`）。经 `metricsPayload` 打包后（`src/main/session.ts:837-844`），界面显示
「没有可用的 GPU 数据」提示条并说明这不影响纯 CPU 推理（`src/renderer/src/components/MetricsPanel.tsx:164-173`），
GPU 卡片显示「无数据」，CPU / 内存 / 吞吐正常。**整条链路没有一处抛异常。**

</details>
