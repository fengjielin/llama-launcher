## 0. 学完这章你能回答什么

## 1. 先看问题

要给 `llama-server` 拼一条命令行，会撞上三个「不查清楚就一定出错」的问题：参数名随版本漂移，
写死一个名字的代码早晚失效；程序可能找不到 exe（用户把便携版 exe 拷到任意目录双击，cwd 不可控）；
很多失败根本不是配置问题（驱动太旧、CUDA 运行时 DLL 不在、模型没下完、显存装不下）——
而最后这一类在点「启动」之前全都能查出来。

这章讲三层代码：**探测**（`helpProbe.ts` / `config.ts`）、**扫描**（`models.ts`）、**预检**（`precheck.ts`），
它们全在 `core` 层、不 import electron，可被 CLI 直接驱动（见 [02 项目全景与四层架构](./02-项目全景与四层架构.md)）。

## 2. 核心概念

### 2.1 Capabilities 与候选名数组：参数漂移的解药

**是什么**：`Capabilities`（`types.ts:45`，含 `has` / `option` / `pick` / `hasValue` / `enumValues`）
把 `llama-server --help` 的纯文本变成「可查询对象」。
**为什么需要**：`helpProbe.ts:5-9` 的注释列了实测到的漂移：

```text
实测例子（b10488）：
  - 草稿模型 KV 量化：`--draft-type-k` 已改名为 `--spec-draft-type-k`
  - 草稿模型路径：`--model-draft` 现在是 `--spec-draft-model`
  - 生成上限：`--predict` / `--n-predict` 两个名字并存
```

**在本项目里**：参数表里每个参数给的不是一个名字，而是按优先级排的**候选名数组**
（`types.ts:84-89` 的 `ParamSpec.candidates`）。例如 `schema.ts:253` 是
`candidates: ["--spec-draft-type-k", "-ctkd", "--cache-type-k-draft", "--draft-type-k"],` ——
新版名在前、老名兜底。运行时挑选动作在 `helpProbe.ts:265-270`：

```ts
// src/core/helpProbe.ts:265-270
    pick(candidates) {
      for (const c of candidates) {
        if (model.byFlag.has(c)) return c;
      }
      return null;
    },
```

于是版本升级不需要改任何拼装代码 —— 这就是「程序不随版本升级而失效」的机制。`types.ts:33` 的措辞
是同一口径：它是「「当前这个 llama.cpp 版本到底认哪些参数」的唯一依据」。

### 2.2 以「应用目录」为锚的探测

**是什么**：`discoverLlamaDir` 在若干起点目录里找 `llama-server.exe`，每个起点向上回溯。
**为什么需要**：便携版双击启动时 cwd 不一定是 exe 目录。`main/index.ts:126-129`：

```ts
// src/main/index.ts:126-129
      // 应用目录作为自动探测的第一起点：便携版双击启动时 cwd 不可靠
      // （可能在 exe 目录、也可能在系统目录），以它为锚才找得到
      // 「项目目录下并列着 llama.cpp」这种常见布局
      { searchDirs: [appDir] },
```

**在本项目里**：`config.ts:473` 的 `discoverLlamaDir`；起点列表由 `session.ts:151-155` 拼成
「应用目录 → cwd → 配置里的 `llama_dir`」。

### 2.3 模型目录布局与分片

**是什么**：`discoverModelLayout` 探「llama.cpp 在哪 → 同级有没有 `models` → 有没有 `presets.ini`」；
`scanModelDir` 把目录里的 `.gguf` 列成可选项。
**为什么需要**：分片模型（`xxx-00001-of-00005.gguf`）是**一个**模型，下拉框里必须合并成一条，
且只能把**第一个分片**传给 `-m`（`models.ts:6-8`）。
**在本项目里**：`config.ts:563`、`models.ts:60`，以及 `models.ts:27-33` 的 `shardCount` /
`declaredShards` —— 两者不等就表示「没下完」。

### 2.4 PE 导入表：判断这份构建需要哪个 CUDA

**是什么**：读 `ggml-cuda.dll` 的 PE 导入表，看它链的是 `cudart64_12.dll` 还是 `..._13.dll`。
**为什么需要**：`precheck.ts:9-11`：「**这份构建需要哪个 CUDA** ← `ggml-cuda.dll` 的 PE 导入表……
这是离线唯一可靠的依据」。目录名和版本号都可能骗人，编译时写死的导入表不会。
**在本项目里**：`pe.ts:90` 的 `readPeImports`，结果经 `precheck.ts:135` 的
`parseCudaRuntimeImports` 变成 `cudaMajor`。

### 2.5 数据驱动的预检

**是什么**：先采集 `PrecheckFacts`（环境事实），再用**纯函数** `buildPrecheckItems(facts)` 生成结论
列表，最后汇总出 `verdict`。
**为什么需要**：采集（碰文件系统、起 `nvidia-smi`）与判定（纯逻辑）分开之后，所有判定分支都能用假
facts 单测覆盖 —— `precheck.test.ts:29-51` 的 `facts()` 就是干这个的。
**在本项目里**：`precheck.ts:273`（判定）与 `precheck.ts:527`（采集）。

### 2.6 为什么要有一个 `format.ts` 叶子模块

**是什么**：只做格式化换算（`formatMiB` / `vramUsageRatio` / `usageBarColor`），不 import 任何 Node 模块。
**为什么需要**：渲染层也要用这些换算，而 `gpu.ts` 为了起 `nvidia-smi` import 了
`node:child_process`。`format.ts:4-7`：

```text
 * 单独成文件的原因：渲染层也要用这些换算（显存大小、占用比例），
 * 而 `core/gpu.ts` 为了采集会 import `node:child_process` —— 一旦渲染层直接引用它，
 * Vite 打包时就会把 Node 内置模块带进浏览器产物并报错。
 * 放在这个"叶子模块"里，主进程与渲染层都能安全引用。
```

这也解释了 `gpu.ts:15-18` 为什么只是 **re-export** 这两个函数：保持旧引用路径不坏，但明确要求
渲染层直接从 `core/format.ts` 引。

## 3. 代码怎么走

### 3.1 一行 help 是怎么被拆开的

解析器的依据是 `helpProbe.ts:22-29` 的几条正则，其中最关键的是选项行本身：

```ts
// src/core/helpProbe.ts:23-25
/** 选项行：必须从第 0 列开始；别名用逗号分隔；值占位符与描述之间是 2+ 空格 */
const OPTION_HEADER_RE =
  /^((?:(?:-{1,2}[A-Za-z0-9][A-Za-z0-9_.-]*)\s*,\s*)*(?:-{1,2}[A-Za-z0-9][A-Za-z0-9_.-]*))(\s.*)?$/;
```

难点写在 `helpProbe.ts:65-79`：help 用**空格数量**同时表达两件事 —— 别名之间是「逗号 + 少量空格」，
而「选项头」与「描述」之间固定用 2 个以上空格。所以拆分实现是：

```ts
// src/core/helpProbe.ts:80-94
function splitPlaceholderAndDescription(rest: string): { placeholder: string; description: string } {
  const parts = rest.split(/\s{2,}/);
  if (parts.length === 1) {
    const only = parts[0].trim();
    // 单空格紧跟 flag（如 `--spec-type none,draft-simple,...`）→ 是值占位符，没有描述
    if (rest.startsWith(" ") && !rest.startsWith("  ")) {
      return { placeholder: only, description: "" };
    }
    return { placeholder: "", description: only };
  }
  return {
    placeholder: parts[0].trim(),
    description: parts.slice(1).join(" ").trim(),
  };
}
```

拿 fixture 里的真行验证（`fixtures/help-b10488.txt:27-28`）：`-n,    --predict, --n-predict N`
后面跟一长串空格再是 `number of tokens to predict (default: -1, -1 = infinity)`，续行是
`(env: LLAMA_ARG_N_PREDICT)`。`OPTION_HEADER_RE` 先切出选项名部分，剩下 ` N         number of ...`
交给上面的函数，按 `\s{2,}` 切成 `[" N", ...]` —— 于是占位符是 `N`、描述是后面那段。

最后一步 `finalizeOption`（`helpProbe.ts:136-151`）把中间结构补全成 `HelpOption`：`primary` 取第一个
长选项（界面展示更好读，`--n-predict` 而不是 `-n`）；`default` **只取第一个逗号之前**
（`(default: 0, 0 = loaded from model)` 整段当默认值没用，`helpProbe.ts:146`）；`env` 从 `(env: X)`
抠出变量名；`deprecated` 只是「描述里出现过 DEPRECATED」的字面判断，所以
`fixtures/help-b10488.txt:87` 的 `--mlock` 会被打标（`helpProbe.ts:120-135`）。

### 3.2 逐行状态机与缩进陷阱

`parseHelp` 是逐行处理的状态机（`helpProbe.ts:198`）。`helpProbe.ts:218-221` 决定「什么才算选项行」：
行首不是空格或制表符、且能被 `parseOptionHeader` 解析出至少一个别名 —— **缩进行绝不是选项行**，
因为 `--split-mode` 的描述里就有一行缩进的 `- row: split weight across GPUs`（`helpProbe.ts:16-17`），
不加这条限制就会多出一个假选项 `- row`（`helpProbe.test.ts:48-56` 钉住了它）。其余非空行一律当
**上一条选项的续行**拼进 `description`（`helpProbe.ts:232-234`），所以 `(env: ...)`、
`allowed values: ...` 都并进同一条选项。解析完把别名摊平成查找表
`for (const f of o.flags) byFlag.set(f, o);`（`helpProbe.ts:237-242`）—— 同一条选项的多个别名指向
**同一个对象**。

### 3.3 能力视图的查询与使用

`hasValue` 的判断是「占位符非空」，`enumValues` 交给 `parseEnumValues`（`helpProbe.ts:271-279`）：
它要认 `[on|off|auto]` 这种竖线列表，也要认 `--spec-type none,draft-simple,...` 这种**把枚举表写在
占位符位置**的（`helpProbe.ts:156-158`）。后者里的 `...` 会被原样当成一个候选值，所以注释警告
「不要拿它去校验用户输入」（`helpProbe.ts:160-161`）。参数表怎么用 `pick`？`args.ts:260` 命中就传，
候选全没命中就记一条 `reason: "unsupported"` 的决策记录并告警
（详见 [05 参数拼装与决策表](./05-参数拼装与决策表.md)）。

`createCapabilitiesWithout`（`helpProbe.ts:293`）把这些查询整体重写一遍，专门用来在单测里**假装某些
参数不存在**，验证旧版本分支 —— 注释说得很清楚（`helpProbe.ts:286-287`）：「真实场景的能力视图永远
来自运行时探测，这个只在单测里出现」。

### 3.4 版本号：`readBuildNumber` 与 stderr 的坑

```ts
// src/core/helpProbe.ts:41-47
export function readBuildNumber(versionText: string): number | null {
  const byFull = BUILD_RE.exec(versionText);
  if (byFull && byFull[1]) return Number(byFull[1]);
  const byShort = BUILD_SHORT_RE.exec(versionText);
  if (byShort && byShort[1]) return Number(byShort[1]);
  return null;
}
```

实测格式是 `version: 0.1.2-dev (build 10488, commit 9d77fa172)`（`fixtures/version-b10488.txt:1`）：
先按 `(build NNNN)` 匹配，匹配不到再找 `b10679` 这种短写法，两种都不中返回 `null`（`helpProbe.ts:35-39`）。
**坑在「去哪找这段文本」**：`launcher.ts:42-43` 的注释说「两个命令的输出都按 **stdout + stderr 拼接**：
llama.cpp 的版本横幅历史上走过 stderr，只读 stdout 会拿到空字符串。」落实在 `launcher.ts:54-55`
（`const versionText = `${version.stdout}${version.stderr}`;`，help 同理）；`llamaProcess.ts:355-356`
重复了同一条约束 —— 底层 `runCapture` 故意**分开收集**两个流。

### 3.5 `discoverLlamaDir` 的探测算法

```ts
// src/core/config.ts:484-496
  for (const start of startDirs) {
    let current = resolve(start);
    for (let level = 0; level <= maxUpLevels; level += 1) {
      for (const candidate of [current, join(current, "llama.cpp")]) {
        if (existsSync(join(candidate, "llama-server.exe"))) return candidate;
      }
      const parent = dirname(current);
      if (parent === current) break; // 已经到盘根，别再往上
      current = parent;
    }
  }
  return null;
```

三件事值得记住：**环境变量优先**且都做存在性判断（`config.ts:478-482`），指向不存在的路径时忽略它
继续回溯而不是返回空（`discover.test.ts:92` 钉的就是这条）；**每层检查两个候选**（该层自己 +
该层的 `llama.cpp/`），判据永远是「这个目录下真的有 `llama-server.exe`」（`config.ts:466`）；
**最多回溯 3 层**，到盘根就停。为什么必须回溯？`config.ts:461-464` 的记录是：便携版 exe 在
`<项目>\llama-launcher\dist\win-unpacked\`，llama.cpp 在 `<项目>\llama.cpp\`，中间隔着三层目录
——「只查"自己 / 自己下面 / 上一级"会漏掉这种常见布局，于是首次运行生成的配置里 `llama_dir` 是空的
（踩过）」。`discover.test.ts:20-33` 复现了这个布局；`<root>\a\b\c\d\e` 这种 5 层深目录则要显式把
`maxUpLevels` 调成 5（`discover.test.ts:35-48`）。

### 3.6 `discoverModelLayout` 与 `resolveModelFile`

`discoverModelLayout` 在 `discoverLlamaDir` 之上再加一层推论（`config.ts:586-591`）：

```ts

  const parent = dirname(llamaDir);
  const modelsDirCandidate = join(parent, "models");
  const modelsDirExists = existsSync(modelsDirCandidate);

  const presetCandidates = [join(parent, "presets.ini"), join(parent, "一键启动脚本", "presets.ini")];
```

判据全是「文件确实存在」（`config.ts:556-558`）。随后用 `parsePresetsIni` 读出 `; default-model =`
约定的预加载模型，**且模型文件真的在**才认（`config.ts:596-605`）—— `modelLayout.test.ts:94-106`
验证「写了但文件不在 → 不预加载，免得启动即失败」。模式结论只有一句：
`mode: presetPath !== "" ? "router" : "single"`（`config.ts:613`）。`resolveModelFile`（`config.ts:529`）

`join(config.models_dir, 模型名 + ".gguf")`（`config.ts:533-536`），router 模式只认它；single 模式
优先 `main_model`，留空才退回它（`config.ts:538-541`）。`mustExist` 开关给界面「填入探测值」用，
启动路径上另有一次存在性检查（`config.ts:525-526`）；`precheck.ts:618-620` 的 `pickModelPath` 转调它。

### 3.7 `scanModelDir`：分片怎么合并

分片的识别规则是 `models.ts:47` 的正则 `SHARD_RE = /^(.*)-(\d{5})-of-(\d{5})$/i`（匹配
`<base>-00001-of-00003`）。每个 `.gguf` 先按基名分桶（`models.ts:86-92`）：文件名去掉 `.gguf` 后去
匹配 `SHARD_RE`，匹配上就取第 1 组当基名、第 2 组当分片序号、第 3 组当声明总数；匹配不上则基名
就是整个文件名、序号记 `1`、声明数记 `null`。

每个桶再合成一条（`models.ts:96-109`）：按 `index` 排序（`models.ts:97` 的注释说「分片乱序读进来是
常态」），`path` 取 `sorted[0]`，体积相加，`shardCount` 是**实际找到的个数**，`declaredShards`
取第一个分片文件名里声明的总数。于是 `declaredShards > shardCount` 就等价于「分片不全」。
`models.test.ts:62-80` 的用例很典型：只有 `m-00001-of-00003.gguf` 时得到 `shardCount === 1`、
`declaredShards === 3`；而 `n-00002.gguf` 因为缺 `-of-NNNNN`，`declaredShards` 是 `null`（不当分片）。
界面据此提示（`ModelPanel.tsx:103-104`）：`if (m.declaredShards !== null && m.shardCount < m.declaredShards)`
时显示「⚠ 只找到 ${m.shardCount}/${m.declaredShards} 个分片」。

### 3.8 `pe.ts` 读 PE 头，以及驱动版本怎么比

为什么不惜手写一个 PE 解析器？`pe.ts:11-12` 的约束是：「**绝不整读文件**：`ggml-cuda.dll` 有
513 MB，只按偏移读 DOS/PE 头、节表与导入目录」；「只解析 PE32 与 PE32+（x86 / x64）」。实现只做
「按偏移读几段」：先验 DOS/PE 签名（`pe.ts:97-106`），再按 `is64` 决定数据目录起始偏移（PE32 是 96、
PE32+ 是 112），取导入目录的 RVA（`pe.ts:122`），经 `rvaToOffset`（`pe.ts:74-82`）用节表换算成文件
偏移。导入描述符数组按 20 字节一条走，直到三个字段全 0 的结束标志（`pe.ts:146-153`），并有
`MAX_IMPORT_DESCRIPTORS = 256` 的硬上限（`pe.ts:46-47`）。**永不抛异常**：任何失败都返回 `{ error }`
（`pe.ts:164-170`），因为「读不出来」本身就是要展示给用户的信息。`pe.test.ts:13-29` 用三种坏输入
各钉一条，`pe.test.ts:31-48` 则在真机有 `llama.cpp` 时断言导入表含 `cudart64_12.dll` /
`cublas64_12.dll` / `nvcuda.dll`。

先纠正一个容易记错的分工：**`sysinfo.ts` 与驱动版本无关** —— 它只做 CPU / 内存采样
（`sysinfo.ts:1-8`：`snapshotCpuTimes` / `cpuUsagePct` / `sampleMemory`），喂给指标面板；
`gpu.ts` 才管显卡，但它只查 `--query-gpu` 那些字段（`gpu.ts:26-38`），**不含** CUDA 版本。
驱动版本与「驱动支持的 CUDA 上限」来自 `nvidia-smi` 头部，由 `precheck.ts:118-125` 解析：

```ts
// src/core/precheck.ts:118-125
export function parseDriverInfo(text: string): { driverVersion: string | null; maxCudaVersion: string | null } {
  const driver = /Driver Version:\s*([0-9]+(?:\.[0-9]+)*)/i.exec(text);
  const cuda = /CUDA Version:\s*([0-9]+(?:\.[0-9]+)*)/i.exec(text);
  return {
    driverVersion: driver?.[1] ?? null,
    maxCudaVersion: cuda?.[1] ?? null,
  };
}
```

实测目标行是 `| NVIDIA-SMI 566.36   Driver Version: 566.36   CUDA Version: 12.7 |`
（`precheck.ts:112-113`）；读不到就返回 `null`，不猜（`precheck.test.ts:69-75`）。比较动作在
`buildPrecheckItems` 里（`precheck.ts:315-325`）：先取 `majorOf(facts.driverMaxCuda)`，再判
`driverMajor < facts.cudaRequiredMajor`。**只比大版本号**，对应 CUDA 的官方兼容规则
「同一大版本内向下兼容」（`precheck.ts:14-15`）。旁注：`precheck.ts:167` 还导出了逐段比较的
`compareVersions`，但它目前只被 `precheck.test.ts:111-121` 使用，判定路径上用的是 `majorOf`。

### 3.9 预检：facts → items → verdict，以及缓存

级别语义在类型定义里（`precheck.ts:32-33`）：

```ts
// src/core/precheck.ts:32-33
/** 自检结论的级别；`error` 表示"这样启动基本一定会失败" */
export type PrecheckLevel = "ok" | "info" | "warn" | "error";
```

一条结论（`PrecheckItem`，`precheck.ts:36-46`）是固定形状：`id`（界面做 key 与去重）、`level`、
`title`（一句话结论）、`detail`（支撑事实）、可选 `suggestion`（该怎么做）。所以加一条检查项只是往
数组里 push 一个字面量对象；界面按 `level` 上色（`PrecheckPanel.tsx:9-17`，四级文案是
「会导致启动失败 / 需要注意 / 信息 / 正常」）。

`buildPrecheckItems` 的分支顺序有意义：**exe 不存在就直接返回**（`precheck.ts:277-286`：push 一条
`id: "exe"` 的 `error`，`suggestion` 指向左侧「构建目录」），后面那些检查全部不做。
`precheck.test.ts:192-194` 钉住了这条：`exeExists: false` 时 `items.length === 1`。之后依次是核心
DLL → 后端构成 → 驱动 vs CUDA → 运行时 DLL → 显卡 → 模型（存在 / 是不是 GGUF / 装不装得下）→
端口 → 预设。总评用 `severityOf`（`precheck.ts:494-505`）取最严重的一项，在 `runPrecheck` 末尾收口
（`precheck.ts:601-604`）。

`runPrecheck` 每次都要起一次 `nvidia-smi`、读一次 PE 头，所以结果缓存在**会话层**，core 层保持
纯函数。`session.ts:737-741`：

```ts
// src/main/session.ts:737-741
  async precheck(force = false): Promise<PrecheckReport> {
    const exe = this.resolveExe(this.config);
    const key = this.precheckKeyFor(exe);
    if (!force && this.lastPrecheck !== null && this.precheckKey === key) return this.lastPrecheck;
```

缓存键是「决定结论的那些字段」拼成的（`session.ts:789-797`）：`exe`、`mode`、`main_model`、
`models_dir`、`preload_model`、`models_preset`、`port` 七项用 `|` 连接。`force` 一路从界面按钮传下来
（`ipc.ts:368` → `main/index.ts:426` → `session.ts:737`）。除 `force` 外，服务启停时还会主动作废
缓存 `invalidatePrecheck()`（`session.ts:801-804`），因为「端口是否被占用」变了。

## 4. 踩过的坑与设计取舍

> **只提示、不拦截。** `precheck.ts:17`：「自检**只提示、不拦截**：误判的代价（用户被挡住）
> 比漏判（用户看到一条警告）大得多。」所以模型占显存超 85% 只是 `warn`，端口被占用也只是
> `warn` 并自动顺延。

> **自检本身永不抛异常。** `precheck.ts:521-522`：「任何一步失败都退化成"该项信息缺失"，
> 其余检查照常进行 —— 自检本身失败不该成为用户的新问题。」例如 `statSync` 失败只让
> `modelSizeMiB` 变成 `null`（`precheck.ts:559-566`）。

> **BOM 会让第一个分节整个消失。** `helpProbe.ts:188-189`：「首字符是 UTF-8 BOM 时先剥掉，
> 否则第一行 `----- common params -----` 匹配不上、整个分节会丢失（实测踩过：用带 BOM 写出的
> help 文件）。」同样的容错在 `gpu.ts:122-123` 又出现一次 —— 这是 Windows 文本处理的通病。

> **`readUInt32LE` 读 GGUF 魔数会对不上。** `precheck.ts:240-241`：「注意按**大端**解释：文件里
> 就是 ASCII 的 `GGUF`（0x47 0x47 0x55 0x46），用 `readUInt32LE` 会得到 0x46554747 而对不上
> （踩过这个坑，单测抓出来的）。」

> **探测规则不能只写在一处。** `config.ts:551-554`：「同一套规则原先只写在 CLI 的 `init` 里，
> 而界面**首次运行生成配置**时只探了 llama.cpp 目录 —— 于是打包版第一次跑拿到的配置是
> `mode: single` + 空的 `models_dir`，用户一切到 router 就被告警"没有任何可用模型"（踩过）。
> 两边共用同一份实现之后，首次运行也能一次探齐，而且这份规则本身可以被单测覆盖。」

## 6. 自测题

<details>
<summary>第 1 题：`-n, --predict, --n-predict N  description (default: -1, -1 = infinity) (env: ...)` 会解析出什么？</summary>

`flags` = `["-n", "--predict", "--n-predict"]`；`primary` = `"--predict"`（第一个长选项，
`helpProbe.ts:143`）；`valuePlaceholder` = `"N"`（按 `\s{2,}` 切开后取第一段）；`default` = `"-1"`
—— **只取第一个逗号之前**，`-1 = infinity` 被丢掉（`helpProbe.ts:146`）；`env` =
`"LLAMA_ARG_N_PREDICT"`（来自续行，拼进 `description` 后才抽得到）；`deprecated` = `false`；
`section` = `"common params"`。`helpProbe.test.ts:31-46` 对 `-n` 的断言与此一致。

</details>

<details>
<summary>第 2 题：目录里只有 `m-00001-of-00003.gguf` 时 `scanModelDir` 返回什么？界面怎么用？</summary>

返回**一条**模型：`name` 是 `"m"`，`path` 指向 `m-00001-of-00003.gguf`（只有第一个分片要传给 `-m`，
`models.ts:6-8`），`shardCount` 是 `1`（实际找到几个），`declaredShards` 是 `3`（文件名里声明的总数）。
两者不等就说明下载没完成（`models.ts:27-32`）。界面在 `ModelPanel.tsx:103-104` 用
`m.shardCount < m.declaredShards` 提示「⚠ 只找到 N/M 个分片」。注意 `n-00002.gguf` 这种缺
`-of-NNNNN` 的名字不算分片，`declaredShards` 是 `null`（`models.test.ts:62-80`）。

</details>

<details>
<summary>第 3 题：为什么自检要读 PE 导入表，而不是看目录名或版本号？</summary>

因为目录名与版本号都可能与真实依赖不符，而导入表是**编译时写死**的链接信息。`precheck.ts:9-11`：
「这份构建需要哪个 CUDA ← `ggml-cuda.dll` 的 PE 导入表…… CUDA 12 构建链的是 `cudart64_12.dll` /
`cublas64_12.dll` / `nvcuda.dll`；CUDA 13 构建则是 `..._13.dll`。这是离线唯一可靠的依据。」
`pe.test.ts:40-47` 在真机有 `ggml-cuda.dll` 时断言这三条依赖确实出现 —— 判据是被测试钉住的。

</details>
