## 1. 任务与验收标准

**任务**：给「采样」分组加一个 **`--seed`（随机种子）** 参数。

选它的理由：它是 `int` 型、不带默认值、不属于预设键，正好覆盖"最小改动"的完整路径。
它在本机这份构建里确实存在 —— 证据是 `fixtures/help-b10488.txt:242`：

```text
-s,    --seed SEED                      RNG seed (default: -1, use random seed for -1)
```

**验收清单**（做完了逐条打勾）：

- [ ] 配置文件里写 `"seed": 42`，`pnpm args` 输出的命令行里出现 `--seed 42`
- [ ] 配置文件里不写 `seed`，命令行里**不出现** `--seed`
- [ ] 界面的「参数」页 →「采样」分组里自动出现一个数字输入框，标签是「随机种子」
- [ ] 界面改动这个值后，命令行预览与决策表同步更新（决策表里那一行写"由命令行传入"）
- [ ] `pnpm test` 全绿，`pnpm typecheck` 零错误
- [ ] 新加的单测在你**故意删掉** `args.ts` 里那行 `emit` 时会失败（证明它真的在守着行为）

## 2. 先想清楚：加一个参数要动哪几个地方

先看结论，再看为什么：

| 文件 | 要不要动 | 做什么 |
| --- | --- | --- |
| `src/core/types.ts` | ✅ 要 | 给 `LauncherConfig` 加字段（这是"配置里允许有这个键"的类型声明） |
| `src/core/schema.ts` | ✅ 要 | 在参数表里登记一条 `ParamSpec`（界面的控件、决策表的标签都从这来） |
| `src/core/args.ts` | ✅ 要 | 加一次 `emit(...)` 调用（告诉 `buildArgs` 这个参数怎么变成命令行） |
| `src/core/config.ts` | ✅ 要 | 默认值、类型收敛、落盘键顺序（三处，都是一行） |
| `src/test/args.test.ts` | ✅ 要 | 加一个测试用例把行为锁住 |
| `src/main/payload.ts` | ❌ **不用** | `buildSchemaPayload` 遍历参数表自动生成界面用的 `SchemaEntry` |
| `src/renderer/src/components/ParamsForm.tsx` | ❌ **不用** | 表单是按 `kind` 自动渲染控件的，不认具体参数 |
| `src/shared/ipc.ts`、`src/preload/` | ❌ **不用** | 只是搬运 `LauncherConfig`，不关心它有哪些字段 |
| `README.md` 的参数清单 | ⭕ 可选 | 想让文档跟上就补一句 |

**为什么界面部分是自动的**：这正是 [02 章](./02-项目全景与四层架构.md) 说的
「参数表是唯一真源」带来的红利 —— 界面不认识任何具体参数名，
它只是把 `SchemaEntry[]` 渲染成控件（`src/renderer/src/components/ParamsForm.tsx`）。
你加参数表一行，界面就多一个控件；这也是为什么 llama.cpp 频繁改参数时这个项目不会腐化。

**唯一的例外**在 `args.ts`：它**不**遍历参数表，而是每个参数手写一次 `emit(...)`。
这是刻意的 —— 有些参数需要特殊处理（跳过条件、值渲染方式、预加载时直传），
统一循环反而写不下这些差异。代价就是"加了参数表还得加一行 emit"，**忘了加不会报错，只是参数永远不生效**，
所以第 5 步的单测必须补上。

## 3. 六步实操

下面每一步都给：**改哪里**（精确到行号锚点）、**加什么**（可以直接抄的代码）、**为什么**。

> 建议每步做完就跑一次 `pnpm typecheck`，出问题能立刻定位到刚改的地方。

### 第 1 步：`src/core/types.ts` —— 给配置加字段

`LauncherConfig` 里「采样」那一段是 `src/core/types.ts:194-202`，长这样：

```ts
  // ---- 采样 ----
  temperature?: number | null;
  top_p?: number | null;
  top_k?: number | null;
  min_p?: number | null;
  presence_penalty?: number | null;
  repeat_penalty?: number | null;
  /** 单次生成上限；必须明显小于 context */
  max_predict?: number | null;
```

在 `repeat_penalty`（第 200 行）之后、`max_predict` 之前插入：

```ts
  /** 随机种子；null = 交给 llama.cpp（-1 表示每次随机） */
  seed?: number | null;
```

**为什么类型是 `number | null | undefined`**：这个项目有一条约定写在 `src/core/types.ts:111-113`——
值为 `undefined` / `null` / 空串的字段**一律不传给 llama-server**，让它用自己的默认值。
`--seed` 的默认值是 `-1`（每次随机），所以"不配"是有意义的状态，用 `null` 表示。

### 第 2 步：`src/core/schema.ts` —— 登记进参数表

找到「采样」那一组（`repeat_penalty` 在第 210 行），在它后面加：

```ts
  {
    key: "seed",
    label: "随机种子",
    group: "sampling",
    kind: "int",
    candidates: ["-s", "--seed"],
    hint: "相同种子 + 相同提示词 → 结果可复现；留空则交给 llama.cpp（每次随机）",
  },
```

四个字段的作用：

| 字段 | 作用 |
| --- | --- |
| `key` | 必须与第 1 步在 `LauncherConfig` 里加的字段名**完全一致** —— 界面靠它读写配置 |
| `group` | 决定控件出现在哪个折叠分组里（可选值见 `PARAM_GROUPS`，`src/core/schema.ts:19-29`） |
| `kind` | 决定用什么控件：`int` → 数字框、`bool` → 开关、`enum` → 下拉框 |
| `candidates` | CLI 参数名候选，**按优先级排列**，运行时由 `caps.pick()` 挑第一个当前版本支持的 |

**关于 `candidates` 的顺序**：这里写 `["-s", "--seed"]`，所以本机这份构建会传 `-s`。
如果你希望命令行里出现的是可读的长名，把它写成 `["--seed", "-s"]` 即可 ——
顺序就是"我优先要哪个名字"。项目里两种风格都有（`-m` / `-c` / `-t` 短名在前，
`draft_model` 是长名在前），选一种与人读日志的舒适度为准。

**关于 `presetKey`**：这里**不填**。理由见第 4 节"变体指南"——
`--seed` 不在 `presets.ini` 和配置预设的键名约定里，填了反而会让命令行不再传它。
文件头的维护约定（`src/core/schema.ts:34-39`）专门提醒过这一条。

### 第 3 步：`src/core/args.ts` —— 加一行 `emit`

找到第 12 节「采样」（第 649 行开始），在 `repeat_penalty` 那条（第 661-667 行）之后加：

```ts
  emit({ key: "seed", label: "随机种子", candidates: ["-s", "--seed"], value: config.seed });
```

就一行。`emit` 会替你把值渲染成 `["-s", "42"]`（默认 `render` 是 `String(value)`），
并按固定的判定顺序记一条决策：
**未配置 → 主动跳过 → preset 接管 → 版本不支持 → 正常传入**（实现见 `src/core/args.ts:230-289`）。

于是你会自动得到这些行为（不用写额外代码）：

| 情况 | 结果 |
| --- | --- |
| `seed` 是 `null` / 没写 | 记 `unset`，命令行不传 |
| 当前 llama.cpp 版本没有 `-s` / `--seed` | 记 `unsupported`，命令行不传，**并往 warnings 里加一条告警** |
| 配置的预设里给某个模型定义了 `seed` 键 | 记 `preset-owned`，命令行不传（若你填了 `presetKey` 才会走到这里） |
| 正常配置了 | 记 `cli`，命令行追加 `-s 42` |

`preloadBypass` 这里**不加**：它只用于"预加载的模型不吃预设"那批参数
（`-c` / `-n` / `-ngl` / `--fit-target` / `--load-mode` 等，见 `src/core/args.ts:679-698`）。
`seed` 不属于这一类。

### 第 4 步：`src/core/config.ts` —— 默认值、类型收敛、键顺序

三处小改动：

**① 默认值**：`DEFAULT_CONFIG` 的采样组在 `src/core/config.ts:49-54`：

```ts
  // 下面这些留 null：由 normalizeConfig 按思考模式填两套官方推荐值
  temperature: null,
  top_p: null,
  top_k: null,
  min_p: null,
  presence_penalty: null,
  repeat_penalty: null,
```

在 `repeat_penalty: null,` 后加 `seed: null,`。

**② 类型收敛**：`normalizeConfig` 里有一组统一转数字的字段，`src/core/config.ts:229-238`：

```ts
  for (const key of [
    "temperature",
    "top_p",
    "top_k",
    "min_p",
    "presence_penalty",
    "repeat_penalty",
  ] as const) {
    out[key] = asNumber(src[key]);
  }
```

把 `"seed",` 加进这个数组。

> 这一步为什么必要：`normalizeConfig` 开头是
> `const out: LauncherConfig = { ...DEFAULT_CONFIG, ...src };`（`src/core/config.ts:193`），
> 也就是说**配置文件里多出来的键会被原样带过来**（这正是索引签名存在的意义）。
> 但如果你不在这里用 `asNumber` 收敛，手工把配置写成 `"seed": "42"`（字符串）时，
> 界面上的数字框会拿到一个字符串，类型和显示都会怪。
> 加了这一行，字符串 `"42"` 会被转成数字 `42`。

**③ 落盘键顺序**：`saveConfigFile` 用一个 `preferred` 列表保证配置文件每次保存的键顺序稳定
（`src/core/config.ts:375-427`，注释解释了原因：同一份配置反复保存不产生满屏 diff）。
在 `"repeat_penalty",`（第 410 行）后面加 `"seed",`。

> 注意：**这一步不做也不会丢数据** —— `saveConfigFile` 在 `preferred` 之后还有一个兜底循环
> （`src/core/config.ts:431-433`），会把没列出的键追加到末尾。
> 加进去只是为了"它出现在采样那一组附近"，属于可读性问题。

### 第 5 步：写单测（这一步最容易被跳过，也最重要）

打开 `src/test/args.test.ts`。文件顶部已经准备好了脚手架：

- `caps`（第 11 行）：用真实的 `fixtures/help-b10488.txt` 解析出的能力视图
- `base(over)`（第 14 行）：一份基线配置，可以用 `over` 覆盖字段
- `build(config)`（第 43 行）：调 `buildArgs` 拿到结果
- `pair(argv, flag)`（第 47 行）：从 argv 里取出 `["-s", "42"]` 这样的相邻两项

在文件末尾（第 399 行之后）加：

```ts
test("采样：seed 配了才传，不配就不传", () => {
  assert.deepEqual(pair(build(base({ seed: 42 })).argv, "-s"), ["-s", "42"]);
  assert.deepEqual(pair(build(base()).argv, "-s"), []);
});

test("采样：seed = -1 也要传（它是 llama.cpp 的合法值，表示每次随机）", () => {
  assert.deepEqual(pair(build(base({ seed: -1 })).argv, "-s"), ["-s", "-1"]);
});
```

两个断言分别守住"配了要传"和"没配不传"；第二个用例守住一个容易想当然的地方 ——
**不要给 `-1` 加 `skipWhen`**，它是真正的合法值，不是"自动"的意思。

跑：

```bash
pnpm test        # 期望：全部通过（原 192 项 + 你新加的）
```

**验收动作**：把第 3 步在 `args.ts` 里加的那行 `emit` 注释掉，再跑 `pnpm test` ——
新加的用例必须**失败**。这一步是在确认你的测试真的在守护行为，而不是写了个永远为真的断言。
确认完记得把注释去掉。

### 第 6 步：四个命令 + 界面，全部验证一遍

```bash
pnpm typecheck     # 1) 类型：0 错误
pnpm test          # 2) 单测：全绿
pnpm args          # 3) 决策表：能看到「随机种子 | 未配置，用 llama.cpp 默认值」
pnpm dev           # 4) 界面：参数页 → 采样 →应该有「随机种子」数字框
```

第 3 步想看到"配了会怎样"，就编辑配置文件（开发态在项目根目录的 `llama-launcher.json`）：

```json
{
  "seed": 42
}
```

再跑 `pnpm args`，输出里应出现 `-s 42`，决策表里那一行的原因变成 `命令行直传`。

第 4 步在界面上填一个值，然后看「决策表」标签页：应该出现
`随机种子 | 由命令行传入 | -s 42`。**如果你只改了 schema 没改 args，这里会是空白**——
这个现象就是"忘加 emit"的典型症状，记住它。

## 4. 变体指南：其它类型的参数怎么加

上面是 `int` 型的最小路径。真实需求往往是下面几种变体。

### 变体 A：这个参数在 `presets.ini` / 配置预设里也有（要填 `presetKey`）

比如 `--repeat-last-n`（`fixtures/help-b10488.txt:257`），如果预设里可能写 `repeat-last-n`，
就必须填 `presetKey`：

```ts
// schema.ts
{ key: "repeat_last_n", label: "惩罚回看长度", group: "sampling", kind: "int",
  candidates: ["--repeat-last-n"], presetKey: "repeat-last-n" }

// args.ts
emit({ key: "repeat_last_n", label: "惩罚回看长度",
       candidates: ["--repeat-last-n"], presetKey: "repeat-last-n", value: config.repeat_last_n });
```

**填了会怎样**：只要**任何一个**模型段里定义过 `repeat-last-n`，
命令行就不再传它，决策表写"preset 接管"。这是 `presetOwns` 的机制
（`src/core/args.ts:220-221` 定义，`248-258` 使用），依据是"实测命令行优先级高于预设"。

**怎么判断该不该填**：看旧脚本 `E:\Code\llama\一键启动脚本\presets.ini` 里有没有这个键。
有就填 —— 否则会出现"命令行把预设精心设的值盖掉"这种很难查的 bug。

### 变体 B：枚举型参数（`kind: "enum"`）

界面要显示下拉框时，给 `enumValues`：

```ts
{ key: "cache_type_k", label: "K cache 类型", group: "spec", kind: "enum",
  candidates: ["--cache-type-k"], presetKey: "cache-type-k",
  enumValues: ["f16", "q8_0", "q4_0"] }
```

`enumValues` 也可以留空 —— 项目里有从 `--help` 的占位符里自动解析候选值的机制
（`Capabilities.enumValues`，见 [04 章](./04-环境探测与预检.md)）。

### 变体 C：纯开关参数（不带值）

`render` 返回 `null` 就只传开关名：

```ts
emit({ key: "no_context_shift", label: "禁用上下文平移",
       candidates: ["--no-context-shift"], value: config.no_context_shift,
       render: () => null });
```

反过来，如果某个参数在新版要求 `on/off`、旧版是纯开关，就参考 `-fa` 的写法
（`src/core/args.ts:444` 起的第 8 节），它会读 `caps.hasValue(flag)` 决定形态 ——
项目的一条原则是**不猜**：占位符是什么样就按什么样传。

### 变体 D：预加载时也要直传的参数

如果这个参数属于"预设里给了值、但预加载模型吃不到"，就要加 `preloadBypass: true`
并让它走 `preloadCtxFromPreset` 那条路（`src/core/launcher.ts:258-271` 负责从预设里把值读出来）。
这是历史上踩过坑的地方，改动前请读 [05 章](./05-参数拼装与决策表.md) 里的 `preloadBypass` 一节。

## 5. 常见错误清单

| 症状 | 原因 | 修法 |
| --- | --- | --- |
| 界面上出现了控件，但命令行里没有 | 忘了在 `args.ts` 里加 `emit` | 加一行 emit（第 3 步） |
| 配置里写了值，保存后再打开就没了 | 键名拼错，或没加进 `LauncherConfig` | `key` 必须与类型字段名逐字一致 |
| 决策表里显示"版本不支持"，但参数明明存在 | `candidates` 里的名字与 `--help` 不一致 | 去 `fixtures/help-b10488.txt` 里搜一遍真实名字 |
| 命令行里参数名变成了别的 | `candidates` 顺序与你预期相反 | 调整顺序（第一个是首选） |
| 配了值却被判成"preset 接管"，命令行不传 | `presetKey` 填了、且某个模型段里有这个键 | 这是正确行为；不想被接管就别填 `presetKey` |
| 数字框里显示成字符串 | 没把键加进 `normalizeConfig` 的数字收敛数组 | 加进 `src/core/config.ts:229-238` 那个数组 |
| 配置文件每次保存 diff 很大 | 新键没进 `preferred` 列表（被兜底循环追加到末尾） | 加进 `preferred`（`src/core/config.ts:375-427`） |
| `pnpm typecheck` 报错说属性不存在 | 只改了 `types.ts` 没同步其它地方，或字段名不一致 | 按报错逐条修；类型检查就是用来抓这个的 |

## 6. 动手练习

### 练习 1（40 分钟，必做）：把 `--seed` 完整做完

按第 3 节的六步做完，勾完第 1 节的验收清单。

**验收标准**：六条全部打勾。特别要求第 6 条（注释掉 emit 时单测会失败）亲手做过一遍。

### 练习 2（30 分钟）：加 `--repeat-last-n`，并观察"预设接管"

**任务**：再加一个参数 `repeat_last_n`（`int`，`candidates: ["--repeat-last-n"]`，
`presetKey: "repeat-last-n"`）。然后做对比实验：

1. 配置里设 `"repeat_last_n": 128`，且**没有任何**模型段提到 `repeat-last-n`
   → `pnpm args` 应该看到 `--repeat-last-n 128`
2. 往配置的 `presets` 里给某个模型加一行 `"repeat-last-n": 64`
   → 再跑 `pnpm args`，命令行里 `--repeat-last-n` **应该消失**，决策表原因变成"preset 接管"

**提示**：预设要生效需要 `mode` 是 `router` 且 `presets` 里有模型段（第 06 章）。

**验收标准**：能解释这两次输出的差别——为什么"预设里出现过"会让命令行主动不传。

### 练习 3（45 分钟，进阶）：加一个纯开关参数

**任务**：加 `--no-context-shift`（`fixtures/help-b10488.txt:429` 里有它，注意它的写法是
`--context-shift, --no-context-shift` 两个名字指向同一项）。要求：

- 配置里 `true` 时命令行出现 `--no-context-shift`
- 配置里 `false` 或 `null` 时不出现
- 界面上是一个开关，不是数字框
- 有单测覆盖上面两条

**提示**：`bool` 型 + `render: () => null`；判断"要不要传"可以用 `skipWhen`
（参考 `src/core/args.ts` 里 `no_webui` / `metrics` 这类开关的写法）。

**验收标准**：`pnpm args` 在两种配置下的输出差异符合预期；决策表能说清"为什么没传"。

## 7. 自测题

**第 1 题**：只改了 `schema.ts` 没改 `args.ts`，界面和命令行分别会是什么表现？为什么？

<details>
<summary>答案</summary>

界面**会出现控件**（表单是按参数表自动渲染的），但**命令行不会有这个参数**。
因为 `buildArgs` 不遍历参数表，它是每个参数手写一次 `emit(...)`（`src/core/args.ts:207-289`）；
没有对应的 emit，这个键就永远不会进 argv。
决策表里连它的行都不会有 —— 这也是一个观察点：**决策表的行数就是 emit 的次数**。

</details>

**第 2 题**：`candidates: ["-s", "--seed"]` 和 `["--seed", "-s"]` 有什么区别？什么时候该选哪种？

<details>
<summary>答案</summary>

区别是**最终传给 llama-server 的参数名**：`emit` 里用 `caps.pick(candidates)`
取第一个被当前版本支持的（`src/core/args.ts:260`）。顺序 = 优先级。
第一种在 b10488 上会传 `-s`，第二种会传 `--seed`。

选哪种看日志可读性：短名让命令行更短，长名让人一眼看懂。
项目里两种都有（`-m`/`-c`/`-t` 用短名，`--spec-draft-model` 用长名）。
它们的**语义完全等价**，llama-server 两个都认。

</details>

**第 3 题**：为什么不给 `seed` 加 `skipWhen: (v) => (v === -1 ? "自动" : null)`？

<details>
<summary>答案</summary>

因为 `-1` 对 `--seed` 来说不是"自动/不传"的意思，而是**合法的具体值**：
`fixtures/help-b10488.txt:242` 写着 `default: -1, use random seed for -1`，
意思是"传 -1 等于每次随机"。

`skipWhen` 是用来表达"这个值等于某个哨兵值时根本不用传"的（比如 `parallel: -1` 表示自动，
传了反而会覆盖服务器的自动推断）。判断依据是**语义**，不是数值长相 ——
这也是为什么练习 1 里专门加了一个 `-1` 的测试用例把这个区别钉住。

</details>

**第 4 题**：做完了这一章，如果你是项目维护者，怎么保证"以后别人加参数不会忘记写单测"？

<details>
<summary>答案</summary>

可以再加一条"元测试"：遍历 `PARAM_SPECS`，断言每个 `key` 都在某次 `buildArgs` 的 `steps` 里出现过
（用一个把所有权都设成非空的配置跑一遍）。这样"加了 schema 没加 emit"会在 CI 里直接失败。

现有代码里已经有类似的思路：`src/test/args.test.ts:389` 那个用例断言
**每个 step 都必须有原因说明**（`step.note.length > 0`），就是在用测试守住"决策表要能自解释"这条规矩。

</details>
