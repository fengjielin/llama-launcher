## 1. 先看问题：手工启动 llama-server 是什么体验

`llama-server` 是一个命令行程序，给它一串参数它就起一个 HTTP 服务。最朴素的一条命令长这样：

```bash
llama-server.exe -m E:\Code\llama\models\Qwen3.8-27B-Uncensored-IQ2_M.gguf -c 32768 -ngl 99 --host 127.0.0.1 --port 8080
```

看着不难。但真实使用中会同时撞上下面这些问题：

| 麻烦 | 具体表现 |
| --- | --- |
| **参数太多** | 本机这份构建（b10488）的 `--help` 里有 **248 个参数**（`README.md:40`）。谁也不可能记住 |
| **参数会改名** | 升级一次 llama.cpp，`--draft-type-k` 变成了 `--spec-draft-type-k`、`--mlock` 被 `--load-mode` 取代（`README.md:152-154`）。写死的脚本一升级就崩 |
| **每个模型一套参数** | 27B 的模型要 `ctx-size 16384`（显存不够），7B 的可以给 `32768`。见 `presets.ini` 里五个模型段的 `ctx-size` |
| **参数之间互相影响** | 上下文长度、KV cache 量化、显存分层三者共同决定「装不装得下 16 GB 显存」，只能试错 |
| **忘了刚才用了什么** | 三天后想复现「上次那个跑得挺快的组合」，只能翻聊天记录 |

这个项目的作者原本就有一个 PowerShell 一键脚本（`E:\Code\llama\一键启动脚本\llama-oneclick.ps1`，
配套一个 `presets.ini`）来解决这些问题 —— 启动器本质上是**把那个脚本里积累的经验固化成一个有界面的程序**，
而且要求极严：仓库 `README.md:196` 写的验收标准是

> **同一份配置，`args` 输出的命令行必须与既有 `llama-oneclick.ps1` 生成的逐项一致。**

这句话很重要，它解释了后面很多设计：启动器不是"重新发明一套参数体系"，而是**忠实复刻已有的正确行为**，
并且用单测把这份一致性锁住。

## 2. 核心概念

### 2.1 llama.cpp 与 llama-server

`llama.cpp` 是一个用 C/C++ 写的推理引擎项目，它编译后会产出一堆可执行文件：

| 程序 | 干什么 |
| --- | --- |
| `llama-server.exe` | **本项目启动的就是它**。一个 OpenAI 兼容的 HTTP 服务端 |
| `llama-cli.exe` | 交互式命令行聊天 |
| `llama-quantize.exe` | 把模型转成另一种量化格式 |
| `llama-bench.exe` | 跑基准测试 |

一次构建还有一份配套的 `.dll`（CUDA 版的 `ggml-cuda.dll` 等）。
**启动器要做的就是：找到这份构建、拼出参数、把 `llama-server.exe` 作为子进程拉起来。**

> 为什么强调"子进程"：启动器本身不含任何推理能力。
> 它是个**调度者**——起进程、读日志、看显存、在需要时把它干净地杀掉（第 07 章）。

### 2.2 GGUF 与量化

**GGUF** 是 llama.cpp 使用的模型文件格式，一个文件里装了权重和元数据。
文件名的规律是 `模型名-量化方案.gguf`，而这正好是本项目里两个关键概念：

- **模型 ID / 模型名** = 文件名去掉 `.gguf`。llama-server 用的就是这个字符串
  （`config.presets` 的段名、`preload_model` 的值都必须是它，见第 06 章）。
- **量化方案**（`IQ2_M`、`IQ4_XS`、`Q4_K_M`…）表示权重被压缩到多少位。
  `Q4` ≈ 4 bit，`IQ2` ≈ 2 bit 但用了更聪明的编码。

本机 `E:\Code\llama\models` 里真实存在的五个模型（体积是磁盘上的实际大小）：

| 文件 | 体积 | 说明 |
| --- | --- | --- |
| `Qwen3.8-27B-Uncensored-IQ4_XS.gguf` | 14.26 GiB | 27B 模型，4 bit 档 |
| `Qwen3.8-27B-Uncensored-IQ2_M.gguf` | 9.9 GiB | 同一个模型，2 bit 档，**体积少 4.3 GiB** |
| `qwen2.5-7b-instruct-q5_k_m.gguf` | 5.07 GiB | 7B，5 bit |
| `meta-llama.Meta-Llama-3-8B-Instruct.Q4_K_M.gguf` | 4.58 GiB | 8B，4 bit |
| `qwen2.5-7b-instruct-q4_k_m.gguf` | 4.36 GiB | 7B，4 bit |

同一个 27B 模型，量化档位不同体积差 4.3 GiB —— 在 16 GB 显存的卡上，这 4.3 GiB
就是"能不能把上下文开到 32768"的分界线。这也是为什么 `presets.ini` 里
IQ2_M 给 `ctx-size = 32768`（第 49 行），而更大的 IQ4_XS 只给 `16384`（第 41 行）。

### 2.3 上下文长度 `-c`、KV cache 与显存

`-c 32768` 表示"最多记住 32768 个 token 的上下文"。它不是免费的：

- 权重占用显存（上表的体积）
- **KV cache** 也占用显存，而且随 `-c` **线性增长**
- 还有计算中间产物（buffer）等开销

所以「模型装得下」不等于「`-c 32768` 装得下」。这个项目的做法是**把每个模型的推荐上下文写在预设里**
（第 06 章），而不是让你每次启动都赌一把。

> 本机实测过一件容易误解的事：**多个请求槽位（slot）共享同一份 KV cache 池**，
> 所以单个请求能用到接近整个 `-c`。这一条在处理"为什么一个请求占了 10018 个 token"时有直接关系。

### 2.4 显存分层 `-ngl` 与 `--fit`

模型有很多层，`-ngl N` 表示"把 N 层放到 GPU 上算"，剩下的层用 CPU 算（慢得多）。
`-ngl 99` 是"能放多少放多少"的惯例写法。

新版本的 llama.cpp 提供了 `--fit` / `--fit-target`：让**它自己**根据显存余量决定放多少层和目标占用。
本项目两者都支持，并且有一条明确的纪律（`README.md:177-178`）：

> **不静默降级**：没有 `--fit-target` 时回退 `-ngl 99` 并**明确告警**，绝不悄悄变成纯 CPU 推理。

也就是说，"降级"这件事必须让你看见，而不是让服务跑起来但慢十倍（第 05 章的"决策表"就是干这个的）。

### 2.5 single 模式与 router 模式

| | single（单模型） | router（多模型） |
| --- | --- | --- |
| 关键参数 | `-m <某个.gguf 路径>` | `--models-dir <模型目录>` |
| 行为 | 只服务这一个模型 | 一次注册目录里所有模型，**按请求里的模型名热切换** |
| 适合 | 我就用一个模型 | 有一堆模型，想让客户端自己挑 |

router 模式是本项目的主力用法。它有两个附带概念：

- **预加载（preload）**：`preload_model` 指定"启动时就把这个模型加载好"，
  否则第一次请求要等几十秒加载。默认值来自 `presets.ini` 里的 `default-model` 约定。
- **`--models-max`**：同时最多加载几个模型（每个都要占显存）。

> 本机最近一次实测：router 模式注册了 5 个模型，日志里能看到
> `Loaded 5 local model presets` / `Available models (5)`（`README.md:238-239`）。

### 2.6 预设（preset）：一个模型一套参数

这是整个项目最核心的概念，值得单独一章（第 06 章）。这里只需要知道：

- 预设 = 「模型名 → 一组参数覆盖」，比如"IQ2_M 用 `ctx-size 32768`、7B 用 `32768`"。
- llama-server 自己认识这种预设（通过 `--models-preset <ini 文件>`）。
- **命令行的优先级高于预设**（实测结论，`README.md:164-165`），所以预设里写过的参数，
  命令行**不能再传**，否则会把预设盖掉 —— 这条规则直接决定了第 05 章 `buildArgs` 的写法。
- 文件名叫 `presets.ini` 的那个是历史格式；本项目现在把预设**直接存在配置的 JSON 里**，
  只在启动时渲染成一份临时 ini 递给服务器（第 06 章讲为什么）。

### 2.7 OpenAI 兼容 API 与 `/health`

llama-server 起好之后对外提供 HTTP 接口，最常用的三个：

| 端点 | 用途 |
| --- | --- |
| `POST /v1/chat/completions` | 聊天补全（OpenAI 格式），任何 OpenAI 客户端都能直接连 |
| `GET /v1/models` | 列出可用模型（router 模式下就是目录里那 5 个） |
| `GET /health` | 健康检查，**判断"服务好了没有"的依据** |

`/health` 的语义有个真实的坑（`README.md:238-239`）：

```
200 = ready（可以用了）
503 = loading（服务在，但模型还没加载完）
连接被拒 = 还没监听端口
```

特别地，**router 模式且未加载模型时实测返回 200 而不是 503** ——
所以判断就绪不能只看状态码是不是 200，还得结合日志。这套判断逻辑在 `src/core/health.ts`（第 07 章）。

## 3. 手工跑一次：把"启动器要自动化的事"亲手做一遍

如果你有 llama.cpp 构建和模型，先手工做一遍，后面读代码会一直有画面感：

```bash
# 1) 起服务（router 模式 + 预加载一个模型）
E:\Code\llama\llama.cpp\llama-server.exe ^
  --models-dir E:\Code\llama\models ^
  -c 32768 -ngl 99 ^
  --host 127.0.0.1 --port 8080

# 2) 另一个终端：看健康状态
curl http://127.0.0.1:8080/health

# 3) 看有哪些模型
curl http://127.0.0.1:8080/v1/models
```

**要观察的四件事**（它们分别对应后面的章节）：

1. 控制台在几秒内开始滚日志 —— 日志是**子进程的 stdout/stderr**，正是第 07 章要读的东西。
2. 端口什么时候真的开始监听 —— 这就是"就绪判断"（第 07 章 `health.ts`）。
3. 打开 `http://127.0.0.1:8080` 有个网页 —— router 模式下的模型下拉框里应该是 5 个模型。
4. 日志里有 `eval time` / `prompt eval time` 这样的行 —— 里面带着 tok/s，
   本项目顺手把它采集成了性能曲线（`README.md:411`）。

没有环境也没关系：`README.md:223-234` 有一段完整的实测记录，逐行读一遍等效。

> 想看看"启动器会怎么拼这条命令"，不用起服务：
> ```bash
> pnpm args        # 只打印命令行 + 每个参数的决策原因
> ```
> 这是读第 05、06 章时最有用的命令。

## 4. 启动器负责的 8 件事

现在把上面的概念对到代码上。这张表是全书的地图：

| # | 要解决的问题 | 对应代码 | 章节 |
| --- | --- | --- | --- |
| 1 | 找到 `llama-server.exe` 在哪 | `src/core/config.ts` 的 `discoverLlamaDir`、`resolveServerExe` | 03、04 |
| 2 | 知道**这个版本**支持哪些参数 | `src/core/schema.ts`（参数表）+ `src/core/helpProbe.ts`（探测） | 04、05 |
| 3 | 把界面上的值拼成命令行 | `src/core/args.ts` 的 `buildArgs` | 05 |
| 4 | 给每个模型一套参数 | `src/core/presets.ts` | 06 |
| 5 | 起进程、读日志、干净地杀掉 | `src/core/llamaProcess.ts`、`logLines.ts` | 07 |
| 6 | 判断"服务好了没有" | `src/core/health.ts` | 07 |
| 7 | 看显存/温度/功耗/速度 | `src/core/metrics.ts`、`gpu.ts` | 07 |
| 8 | 让界面看到的东西和真实执行的一致 | `src/shared/ipc.ts` + 分层纪律 | 02、08、09 |

第 8 条值得先说一句：本项目的核心承诺是**「界面上显示的命令行 === 实际启动的命令行」**。

## 5. 踩过的坑与设计取舍

> **`[defaults]` 段不是被忽略，而是被当成一个模型**（`README.md:240-247`）。
> 旧的 `presets.ini` 里有 `[defaults]`（见 `presets.ini:30`），llama-server 会给它建一个名叫
> `defaults` 的假模型：日志从 `Available models (5)` 变成 `(6)`，网页下拉框多一项，还白占一个槽位。
> 现在预设由启动器渲染，只写真实模型段，这个问题从根上消失了。

> **命令行的优先级高于预设**（`README.md:164-172`）。所以"预设里配过的键，命令行不能再传"。
> 例外是**预加载的模型不吃预设**（实测 `ctx` 被忽略、`--fit` 还会把它压到 4096），
> 此时必须反过来由命令行直传 —— 这条例外规则导致过一次回归：预设里一旦写了 `n-predict`，
> 预加载模型就被判成"预设接管"而**完全不传 `-n`**，于是以 llama.cpp 默认的"无限"运行。

> **参数改名不是假设，是实测**：本次开发就撞上 `--draft-type-k` → `--spec-draft-type-k`、
> `--model-draft` → `--spec-draft-model`、`--mlock` 被 `--load-mode` 取代并标 `DEPRECATED`
> （`README.md:152-154`）。所以本项目**不写"b10488 用什么"的分支表**，而是每个参数带一组候选名，
> 运行时挑第一个被支持的（第 04 章）。

> **"约 9.8 tok/s"是作者在 `presets.ini:37` 注释里留下的实测值**，还带着"想要更激进就改 ctx-size 8192"的建议。
> 这类经验值正是"每个模型一套预设"存在的理由，也是启动器要把它搬进 JSON 配置的原因（第 06 章）。

## 7. 自测题

**第 1 题**：这个启动器启动的可执行文件是哪个？它和 `llama.cpp` 是什么关系？

<details>
<summary>答案</summary>

启动的是 `llama-server.exe`（`llama.cpp` 这份构建里的 HTTP 服务端程序）。
`llama.cpp` 是推理引擎项目本身，一次构建会产出 `llama-server.exe`、`llama-cli.exe`、
`llama-quantize.exe` 等多个可执行文件和配套 `.dll`。
启动器不含推理能力，它只是找到并把 `llama-server.exe` 作为子进程拉起来。

</details>

**第 2 题**：为什么"预设里定义过的参数，命令行不能再传"？

<details>
<summary>答案</summary>

因为实测**命令行的优先级高于预设**（`README.md:164-165`）。如果命令行也传了同一个参数，
就会把预设里为该模型精心设置的值得盖掉 —— 于是"预设"等于失效。
所以 `buildArgs` 引入 `presetOwns` 判断：某个键在任何模型段里出现过，命令行就跳过它，
并在决策表里标明原因是"preset 接管"。

例外：预加载的模型不吃预设，此时反而**必须**由命令行直传（`preloadBypass`），这是同一个机制的反面。

</details>

**第 3 题**：`/health` 返回 200 就能说明"模型加载好了，可以发请求了"吗？

<details>
<summary>答案</summary>

不能。`/health` 有三种情况：200 = ready、503 = loading（服务在但模型未加载完）、连接被拒 = 还没监听。
但本机实测发现 **router 模式且未加载模型时也会返回 200**（`README.md:228-229`），
所以判断就绪要结合日志（比如是否已经出现模型加载完的记录）。

</details>

**第 4 题**：为什么同样是一个 27B 模型，`IQ2_M` 反而能支持更长的上下文？

<details>
<summary>答案</summary>

因为它的量化更激进（2 bit 档），权重只占 9.9 GiB；而 `IQ4_XS`（4 bit 档）占 14.26 GiB。
上下文长度对应 KV cache，也吃显存，所以权重省下来的 4.3 GiB 可以换成更长的上下文
（`presets.ini` 里就是 `32768` vs `16384`）。代价是量化更低，输出质量会下降。

</details>
