## 1. 先看问题：为什么不能一个文件写完

启动器这类程序最自然的写法是「一个 `main.js`：开窗口 → 读配置 → 拼命令 → 起进程 → 把日志塞进界面」。
一开始能跑，但很快会遇到三个具体麻烦：

1. **GUI 与 CLI 会慢慢不一致**。项目里有一个 CLI 入口（`src/cli.ts`，494 行）和一套 GUI。
   如果两处各写一遍拼命令的逻辑，改了一处忘了另一处，就会出现「命令行启动没问题、界面启动少了个参数」。
2. **逻辑没法测**。拼参数、解析日志、判断显存够不够，这些都是纯逻辑；但如果它们和窗口、
   托盘、对话框糊在一起，就只能"手工点一遍"来验证。
3. **换壳成本极高**。今天用 Electron，明天想换成 Tauri 或者一个纯网页版，业务逻辑如果和 Electron API 长在一起，
   等于重写。

这个项目的答案是把代码切成四层，并规定**依赖只能单向流动**。

## 2. 核心概念

### 2.1 四个层，以及依赖方向

```text
        ┌──────────────────────────────────────────────┐
        │  renderer  React 界面                        │
        │  只管显示与交互，通过 window.llamaApi 拿数据 │
        └───────────────┬──────────────────────────────┘
                        │  window.llamaApi（contextBridge 注入）
        ┌───────────────▼──────────────────────────────┐
        │  preload   唯一跨边界处，把能力收敛成一个接口│
        └───────────────┬──────────────────────────────┘
                        │  IPC 通道（契约在 shared/ipc.ts）
        ┌───────────────▼──────────────────────────────┐
        │  main      Electron 主进程：窗口、托盘、编排 │
        └───────────────┬──────────────────────────────┘
                        │  直接 import（同进程）
        ┌───────────────▼──────────────────────────────┐
        │  core      零依赖纯逻辑：配置、探测、拼装…  │
        │  （可被 CLI 直接调用，不含任何 Electron 代码）│
        └──────────────────────────────────────────────┘
```

| 层 | 目录 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| **core** | `src/core/` | 配置归一化、目录探测、参数拼装、预设渲染、进程管理、日志解析、健康检查、指标解析 | **不 import electron**、不开窗口、不弹对话框 |
| **main** | `src/main/` | 窗口、托盘、单实例、IPC 注册、业务编排（`LauncherSession`） | 不自己拼命令行（交给 core） |
| **preload** | `src/preload/` | 用 `contextBridge` 把一组方法暴露成 `window.llamaApi` | 不写业务逻辑 |
| **renderer** | `src/renderer/` | React 界面：表单、决策表、日志、曲线 | 不拼命令行、不碰文件系统 |

### 2.2 `core` 零依赖这条纪律，具体是什么意思

两个含义，都可以当场验证：

**① 不引用 Electron。** 整个 `src/core/` 目录里搜 `from "electron"` 是**零命中**：

```bash
grep -rn 'from "electron"' src/core     # 没有任何输出
```

**② 只用 Node 内置模块，且能靠 Node 原生类型擦除直接运行。**
`src/core/types.ts:1-6` 把这条约束写在文件头上：

```ts
/**
 * core 层公共类型。
 *
 * 约束：本目录所有 .ts 都必须能被 Node 原生类型擦除直接运行
 * （无 enum / 无 namespace / 无构造函数参数属性 / 类型导入必须写 `import type`）。
 */
```

带来的直接好处：**没有编译步骤**。`node src/test/run-tests.ts` 能直接跑 `.ts` 源码（只要 Node ≥ 22.18），
`src/cli.ts` 也能直接被 `node` 执行 —— 于是"验证 core"这件事不需要先构建整个应用。

> 代价是写法上要小心：不能用 `enum`（用字符串联合类型代替，比如 `ServerMode`），
> 类型导入必须写 `import type`（否则擦除后会留下运行时的 import 语句）。

### 2.3 编排层：`prepareLaunch`

`core` 里最重要的一个函数是 `prepareLaunch`（`src/core/launcher.ts:195`）。
它的定位写在文件头（`src/core/launcher.ts:1-6`）：

```
 * 启动编排层：把「配置 → 探测 → presets → 命令行」串起来。
 *
 * CLI 和 Electron 主进程都只调这一层，保证 GUI 与命令行行为完全一致 ——
 * 这样才谈得上"同一份配置产出同一条命令行"。
```

也就是说：**无论是 CLI 还是界面，最终都调同一个 `prepareLaunch`**。
这是"看到的命令 === 启动的命令"的第一半保证；第二半在 `src/main/session.ts:513` 的注释里：

```
 * 也正因为它和 `start()` 共用 `prepareLaunch`，"看到的命令"才等于"启动的命令"。
```

（预览走 `prepareLaunch`，启动也走 `prepareLaunch`，两者拿到的是同一个结果。）

### 2.4 IPC 契约放在 `shared`

`src/shared/ipc.ts` 是 main / preload / renderer **三端共享**的东西，但里面只有两类内容：
**通道名常量**（`IPC.xxx`）和**类型**。设计理由写在文件头（`src/shared/ipc.ts:1-9`）：

```
 * 这里只放**类型与通道名**：core 里的业务类型原样复用（`import type`，编译后被抹掉），
 * 避免界面层另造一套 DTO 然后跟 core 慢慢漂移。
 *
 * `LlamaApi` 是全程序唯一的前端调用面：preload 实现它，renderer 只认它。
 * 将来若把 Electron 换成别的壳，只要新壳再实现一遍这个接口即可。
```

这段注释值得记住：**界面层不定义自己的数据结构**，直接用 core 的类型（`LauncherConfig`、`BuildStep`…）。
core 改了字段，界面编译期就会报错，而不是运行时才发现对不上。

### 3.2 一次「启动」的完整数据流

这是本章最重要的一节。跟着下面 10 跳走一遍，后面每章就都有了位置感。

**第 1 跳：界面按钮 → 状态中枢**
按钮在 `src/renderer/src/components/CommandBar.tsx`，它调用的是 `useLauncher()` 返回的 `start` 回调
（`src/renderer/src/hooks/useLauncher.ts:424`）。界面组件自己**不拼命令行**，只把当前配置交出去。

**第 2 跳：状态中枢 → preload 桥**
`useLauncher` 里调 `api.start(config)`，而 `api` 就是 `window.llamaApi`（第 132 行附近有 `bridgeMissing` 判断：
拿不到这个对象就说明界面是被浏览器直接打开的，显示一段提示而不是白屏）。

**第 3 跳：preload → IPC 通道**
`src/preload/index.ts:31`：

```ts
start: (config: LauncherConfig) => ipcRenderer.invoke(IPC.start, config),
```

通道名是 `IPC.start`，它的字符串值定义在 `src/shared/ipc.ts:40`（`start: "llama:start"`）。

**第 4 跳：IPC 通道 → 主进程**
`src/main/index.ts:428`：

```ts
ipcMain.handle(IPC.start, (_e, config: LauncherConfig) => s().start(config));
```

注意这一跳**极薄**：主进程只做转发，业务在 `s()` 里（即 `LauncherSession` 实例）。

**第 5 跳：主进程 → 编排层**
`src/main/session.ts:554` 是 `async start(config: LauncherConfig)`。注意它**不自己拼命令行**，
而是先调自己的 `preview()`（`src/main/session.ts:557`），由 `preview()` 去调 `prepareLaunch`
（`src/main/session.ts:530`，导入语句在 `src/main/session.ts:25`）。
「预览」和「启动」走的是同一个 `preview()`，于是拿到的是同一份结果 ——
`src/main/session.ts:513` 的注释说的就是这件事："也正因为它和 `start()` 共用 `prepareLaunch`，
'看到的命令'才等于'启动的命令'"。

**第 6 跳：编排层按顺序做六件事**（`src/core/launcher.ts`，函数从第 195 行开始，
六个步骤在代码里就是 `// ---- 1.` 到 `// ---- 6.` 六段注释）

| 步骤 | 做什么 | 行号 |
| --- | --- | --- |
| ① 找 exe | 配置里的路径优先；配了但不存在就告警并转为自动探测 | 198-215 |
| ② 探测能力 | 现跑 `--version` + `--help`，产出 `Capabilities` | 217-229 |
| ③ 渲染预设 | 配置里的 JSON → ini 文本 → 写进 `%TEMP%` 临时文件 | 231-252 |
| ④ 解析预加载模型 | 校验文件存在，并从它的预设里读出 `ctx-size` / `n-predict` | 254-271 |
| ⑤ single 模式兜底 | 主模型没填时，按 `preload_model` + `models_dir` 推出路径 | 273-286 |
| ⑥ 拼命令行 | 调 `buildArgs`，得到 `argv` + 决策表 `steps` | 288-299 |

**第 7 跳：拼装（纯函数）**
`buildArgs`（`src/core/args.ts`）输入配置 + 能力视图 + 各种已解析好的路径，
输出 `argv`（真正给进程的参数数组）、`env`、`steps`（每个参数为什么传/不传）、`warnings`。
它**不碰文件系统**，所以能直接被单测覆盖（第 05 章）。

**第 8 跳：起子进程**
`LauncherSession` 里持有的是同一个 `LlamaServer` 实例（`src/main/session.ts:109`），
它最终执行 `spawn`（`src/core/llamaProcess.ts:223`）。进程状态机在 `src/core/llamaProcess.ts:117` 起的
`class LlamaServer`。

**第 9 跳：日志回流（这是反向的推送流）**

| 跳 | 位置 | 代码 |
| --- | --- | --- |
| ① | `src/main/session.ts:612` | `this.events.onLog?.(push);` |
| ② | `src/main/index.ts:118` | `onLog: (entry) => win?.webContents.send(IPC.pushLog, entry)` |
| ③ | `src/preload/index.ts:61` | `ipcRenderer.on(IPC.pushLog, listener)` |
| ④ | `src/renderer/src/hooks/useLauncher.ts:285` | `const offLog = api.onLog((entry) => { ... })` |
| ⑤ | `src/renderer/src/components/LogPane.tsx` | 渲染到日志面板 |

状态与指标走完全相同的形状：`src/main/session.ts:616`（`onState`）、`src/main/index.ts:120`/`124`、
`src/preload/index.ts:69`、`src/renderer/src/hooks/useLauncher.ts:292`/`296`。

**第 10 跳：就绪与状态**
`health.ts` 轮询 `/health` 得到就绪状态，通过 `pushState` 推回界面，状态栏显示
「端口已监听（等待 xxx ms）」这类文案（第 07 章）。

> 把这条链记住，你就能定位任何"界面上的某个数字是从哪来的"问题：
> 顺着 `useLauncher` 的状态字段向上找 API 方法，再查 `IPC` 通道名，就能跳到主进程与 core。

### 3.4 三条不变式，以及怎么自查

学这个项目最有效的办法是记住三条"不许违反"的规矩，读代码时反复用来检验：

**不变式 1：界面不拼命令行。**
自查：`grep -rn "buildArgs" src/renderer` → 零命中。界面只显示 core 拼好的 `command`。

**不变式 2：core 不依赖 Electron。**
自查：`grep -rn 'from "electron"' src/core` → 零命中。

**不变式 3：IPC 契约只有一份。**
自查：看 `src/shared/ipc.ts` 是否只有 `import type`；`src/preload/index.ts` 是否逐条实现了 `LlamaApi`。
如果 preload 里出现了一个 `LlamaApi` 没有的方法，说明契约被绕过了。

## 4. 踩过的坑与设计取舍

> **为什么 `format.ts` 要单独拆出来。** 界面层需要格式化数字（如 `formatMiB`），
> 但它**不能 import 任何依赖 Node 的模块**（渲染层没有 Node 环境）。
> 所以凡是"界面也要用的纯函数"都被放进这个叶子模块，它不 import 任何东西 —— 这是分层的必要代价。

> **`preload` 编译产物是 `.cjs`。** 主进程里写的是 `../preload/index.cjs`（`src/main/index.ts:37`），
> 而不是 `.js`。原因是 preload 在 Electron 里默认按 CommonJS 加载，而项目其它部分是 ESM。
> 这个 `.cjs` 由 `electron-vite` 构建产出（第 10 章）。

> **"薄转发"是刻意的。** `src/main/index.ts:424-528` 那 26 个 `ipcMain.handle` 几乎都是
> `(_e, x) => s().method(x)`。这样做的好处是：业务逻辑全在 `LauncherSession` 里，
> 它不依赖窗口，将来换壳（或写测试）时不用动业务代码。

> **渲染层要能"优雅地坏掉"。** 如果直接用浏览器打开界面（没有 Electron 注入的桥），
> `window.llamaApi` 是 `undefined`。项目没有白屏，而是显示一段提示告诉你怎么正确启动
> （`src/renderer/src/hooks/useLauncher.ts:132` 的 `bridgeMissing`，界面在 `App.tsx:33-51` 处理）。

抄下来，然后对每一个注明：

- 它用到了哪个 core 模块
- 它会往 `warnings` 里写什么情况
- 它对应本手册哪一章

**验收标准**：六个步骤都能对上一个模块；能指出哪一步"失败也不中止，只降级"（提示：探测那一步）。

## 6. 自测题

**第 1 题**：为什么 `core` 不允许 `import electron`？请说出至少两个具体好处。

<details>
<summary>答案</summary>

1. **可测试**：core 是纯逻辑，`node src/test/run-tests.ts` 能在没有 Electron 的情况下直接跑，
   不需要启动窗口，也不受 Electron 环境影响。
2. **可被 CLI 复用**：`src/cli.ts` 直接调 `prepareLaunch`，于是 CLI 与 GUI 行为天然一致
   （`src/core/launcher.ts:1-6` 的注释就是这个意思）。
3. **换壳成本低**：将来换成别的桌面壳，core 一行不用改。

另外还有一个隐蔽好处：core 只用 Node 内置模块 + 原生类型擦除，所以**没有构建步骤**。

</details>

**第 2 题**：`prepareLaunch` 干了六件事，请按顺序说出来。为什么"找 exe"失败会抛异常，而"探测能力"失败只告警？

<details>
<summary>答案</summary>

六件事：① 找 `llama-server.exe` → ② 跑 `--version` / `--help` 得到能力视图 → ③ 把配置里的预设渲染成临时 ini
→ ④ 解析预加载模型（并读出它的 `ctx-size` / `n-predict`）→ ⑤ single 模式没填主模型时按
`preload_model` 兜底推出路径 → ⑥ 调 `buildArgs` 拼命令行。
（`src/core/launcher.ts:195` 起，每个步骤都有 `// ---- N.` 注释。）

- 找 exe 失败**必须抛**：连程序都没有，继续下去毫无意义（`src/core/launcher.ts:211-215`）。
- 探测失败**只能降级**：拿不到 `--help` 时按"空 help"继续，结果是大部分参数被判成"版本不支持"
  而不会被误传（`src/core/launcher.ts:224-227`）。宁可少传参数并告警，也不要因为一次探测超时就拒绝启动。

</details>

**第 3 题**：日志从子进程到界面的这条链，中间一共经过几跳？为什么不让 core 直接调用界面的函数？

<details>
<summary>答案</summary>

五跳：`LauncherSession` 的 `events.onLog`（`src/main/session.ts:612`）→ 主进程
`win.webContents.send(IPC.pushLog, ...)`（`src/main/index.ts:118`）→ preload 的 `ipcRenderer.on`
（`src/preload/index.ts:61`）→ 渲染层 `api.onLog(...)` 订阅（`src/renderer/src/hooks/useLauncher.ts:285`）
→ 组件渲染。

不让 core 直接调界面的原因：core 不能依赖 Electron（不变式 2）。
它只把事件交给"回调函数"（`events` 字段），谁来实现这个回调由 main 决定 —— 这就是依赖倒置。

</details>

**第 4 题**：如果你想加一个"启动前自动检查磁盘剩余空间"的功能，应该改哪一层？

<details>
<summary>答案</summary>

**core**：写一个纯函数（读磁盘空间在 Node 里是允许的，`node:fs` 属于内置模块），
最好放在 `precheck.ts` 那种数据驱动的检查项里，并配一个单测。
**main**：如果需要在界面上展示结果，就把结果塞进已有的载荷（如 `PrecheckReport`）。
**renderer**：只有当你想"在界面上多显示一项"时才改。
所以大多数功能是「core 加逻辑 + 界面顺带显示」，不需要在主进程里新写业务代码。

</details>
