> **前置**：[02 项目全景与四层架构](./02-项目全景与四层架构.md)。

## 0. 学完这章你能回答什么

- 为什么 `LauncherConfig` 里几乎每个字段都可选（`?`），而唯一的必填字段 `llama_dir` 默认值却是空串？
- 配置里写 `"context": 64`，为什么最终传给 llama-server 的是 `65536`？为什么 `null` 和空串不是一回事？
- 配置文件到底放在哪？为什么打包版的配置可能在 exe 旁边、也可能在 `%APPDATA%`？
- 「应用设置」和「启动配置」是同一份文件吗？开机自启那个开关存在哪儿？

## 1. 先看问题

启动器要干的活，本质只有一件事：**攒出一行命令行，然后 `spawn` 它**。而 llama-server 光
`--help` 里就有上百个参数，所以「攒什么」必须有明确的数据结构。不用配置对象会碰到三条真实路径：

1. 你想把上下文从 32K 调到 64K。没有配置文件，就得改代码里的常量再重启程序。
2. 你的配置是手写的，里面 `"parallel": "-1"` 是**字符串**，`"cpu_moe": 0` 含义还含糊不清。
   拼命令行时直接 `String(value)`，时对时错。
3. 你把打包版拷到 U 盘给同事。如果配置写在 `%APPDATA%`，他拿到的是「一个不会用的程序 + 一堆残留」。

于是本章的三样东西就出来了：**一个类型**（`LauncherConfig`）、**一套归一化规则**（`normalizeConfig`）、
**一套落点策略**（`paths.ts`）。

## 2. 核心概念

### 2.1 `LauncherConfig`：一次启动所需的全部输入

**是什么**：一个普通对象，字段名是「启动器认得的旋钮」，值是「这次启动用什么值」。
界面改的是它、存到磁盘的是它、拼命令行时读的还是它 —— 只有一份数据结构，就不会出现
「界面显示 A、实际传给服务器 B」的假象。定义在 `src/core/types.ts:115`：

```ts
// src/core/types.ts:111-115
 * 约定：值为 `undefined` / `null` / 空串的字段一律**不**传给 llama-server
 * （让 llama.cpp 用它自己的默认值），而不是传一个"看起来安全"的值。
 * 末尾的索引签名用于保留配置里不认识的额外键，避免丢数据。
 */
export interface LauncherConfig {
```

只有第一个字段必填（`src/core/types.ts:117-120`）：`llama_dir: string` —— 它是整条链路的锚点，
exe 路径与模型目录都从它推；其余可选，因为配置可能是别人手写的 JSON，只写一个 `port` 也应该能跑。
但它在类型上必填的同时，默认值却是空串（`src/core/config.ts:30`），靠自动探测去填。末尾的索引签名
（`src/core/types.ts:234-236`，`[key: string]: unknown`）是「不丢数据」的保险：塞一个
`"我的笔记": "..."` 进去，启动器不报错、不删它、不拼进命令行，还会原样写回文件。

### 2.2 三值约定：`undefined` / `null` / 空串都不传

llama.cpp 自己有一套调优过的默认值，启动器若自作主张填一个「看起来安全」的值（线程数填 8、
`-ngl` 填 0），就是拿猜的值覆盖官方默认值。所以「不传」必须是一等公民（`src/core/types.ts:111-112`）。
界面负责把「清空输入」翻译成 `null`：「清空输入表示"不传这个参数"，一律写回 `null`」
（`src/renderer/src/components/ParamsForm.tsx:35-36`），落在下拉框空选项 `:59`、文本框清空 `:83`、
数字框清空 `src/renderer/src/components/ui.tsx:141-143`。反直觉的是：归一化后的 `null`
会被**写进文件**（表示「交给 llama.cpp 决定」），`undefined` 会被跳过。

### 2.3 `DEFAULT_CONFIG` 与 `normalizeConfig`：为什么必须有归一化

`DEFAULT_CONFIG`（`src/core/config.ts:29`）是「什么都没配」时的基线；`normalizeConfig`
（`:190`）把任意来源的 JSON 收敛成可用配置，并产出一串给用户看的告警。来源不可信是常态：手写的、
老版本留下的、从别人那儿拷的。要处理的事列了 7 条（`:176-186`），其中两个默认值选择值得记：

```ts
// src/core/config.ts:34-37
  context: 32768,
  // 取上面那个窗口的一半（规则见 presets.ts 的 recommendedMaxPredict）：
  // 太小会让 32K 窗口的模型只能输出 8K；太大（等于窗口）会让一次跑飞的回复占满窗口
  max_predict: 16384,
```

采样参数在默认值里**故意留 `null`**（`src/core/config.ts:48-54`），因为它们由归一化按思考模式
填两套官方推荐值（理由见 `:26-27`）。

### 2.4 配置与数据的落点：三选一

有且只有三种结果：开发态放项目根目录、打包后可写就放 exe 同级、只读就退回 `%APPDATA%`。
矛盾写在 `src/main/paths.ts:3-5`：Electron 默认把数据放 `%APPDATA%\<应用名>`，那就成了
「绿色的 exe + 散落一地的 AppData」，拷走文件夹带不走配置。实现是 `chooseDataLayout()`（`:135`），
主进程在模块加载时就算出落点（`src/main/index.ts:76-81`），便携模式下还会把整个 `userData`
搬过去（`:82-86`）。

### 2.5 「启动配置」和「应用设置」是两回事

`llama-launcher.json` 是启动配置（影响 llama-server）；`llama-launcher-settings.json`
是应用设置（影响启动器自己）。两者写入时机不同：启动配置「改了要点保存、不保存不生效」，
应用设置「点一下开关就该立刻生效并落盘」。混成一份，关窗行为这种运行时偏好就要跟一堆启动参数
一起走保存流程。设置只有两个持久化字段：`openAtLogin`（开机自启）与 `minimizeToTray`（关窗缩托盘），
见 `src/shared/ipc.ts:319-324`；落盘位置与容错策略见 `src/main/settings.ts:1-7`。

### 2.6 `ParamSpec`：一份声明驱动整个参数表单

一张表，每项描述一个 llama-server 参数：配置键名、显示名、分组、控件类型、CLI 参数名候选、
对应的 preset 键名、说明文案。理由写在 `src/core/schema.ts:3-4`：GUI 表单、命令行拼装、
preset 占位判断三者都读这一张表，避免把参数知识散进 UI 代码（llama.cpp 参数改动频繁，散着写必然腐化）。
表在 `src/core/schema.ts:43`，一条完整的声明长这样：

```ts
// src/core/schema.ts:111-119
  {
    key: "context",
    label: "上下文长度",
    group: "context",
    kind: "int",
    candidates: ["-c", "--ctx-size"],
    presetKey: "ctx-size",
    hint: "ctx 翻倍 KV cache 也翻倍；16G 显存跑 27B 建议 16384 起",
  },
```

`candidates` 按优先级列出**同一语义在不同版本里的全部名字**（`src/core/types.ts:84-89`），运行时挑第一个
当前版本支持的 —— 所以 `--spec-draft-type-k` 这种改名不会让启动器失效。`enumValues`（`:92-93`，枚举候选）
与 `hint`（`:94-95`，tooltip 文案）则决定界面上是下拉框还是文本框、鼠标悬停时显示什么。

## 3. 代码怎么走

主线四步：**读文件 → 归一化 → 存内存 → 按固定顺序写回**（`loadConfigFile` → `normalizeConfig`
→ 内存里的 `config` → `saveConfigFile`）；落点决定读哪个文件，拼命令行是
[05 参数拼装与决策表](./05-参数拼装与决策表.md) 的事。

### 3.1 宽松转换：三个小函数决定了归一化的性格

```ts
// src/core/config.ts:130-134
function asNumber(v: unknown): number | null {
  if (typeof v === "number" && Number.isFinite(v)) return v;
  if (typeof v === "string" && v.trim() !== "" && Number.isFinite(Number(v))) return Number(v);
  return null;
}
```

布尔函数（`src/core/config.ts:148-156`）**故意不认** 0/1 —— 注释（`:141-143`）说「老配置里
`"cpu_moe": 0` 更像"数量"而不是"开关"，贸然当成 `false` 会改变语义」。字符串版 `asString`
（`:116-119`）只接受 trim 后非空的字符串。`think` 同属一路（`normalizeThink`，`:97-108`）：
`true/false`、`"ON"`、`"yes"` 都能识别，`"看不懂"` 返回 `null`，**绝不猜一个模式**（`:91`）。

### 3.2 关键分支（顺序有意义）

它从一行「铺默认值」开始（`src/core/config.ts:192-193`）：非对象输入被当成空对象，所以垃圾输入
不抛异常（`:171-173`）；`...src` 会原样搬进未知键。然后逐条分支：

**（1）context 单位识别** —— 只识别 + 明确告警，不静默改数：

```ts
// src/core/config.ts:199-207
  const ctxRaw = asNumber(src["context"]);
  if (ctxRaw !== null && ctxRaw > 0 && ctxRaw <= 512 && src["contextUnit"] === undefined) {
    const tokens = ctxRaw * 1024;
    out.context = tokens;
    warnings.push(
      `配置里的 context=${ctxRaw} 小于等于 512，按「K」解释为 ${tokens} tokens。` +
        `若你原本就想要 ${ctxRaw} tokens，请把 context 显式改成 ${ctxRaw} 并加 "contextUnit": "tokens"`,
    );
  }
```

想显式声明「我就要 64 个 token」就加 `"contextUnit": "tokens"` —— 它并不在 `LauncherConfig` 里，
能被读到纯粹是因为索引签名。

**（2）模式推断**（`:262-269`）：显式 `mode` 优先；没写就看有没有 `models_dir`（有目录即 router），
都没有则 `single`。**（3）预设形状收敛**（`:275-307`）：只检查「模型名 → 参数表」的形状，
坏条目丢掉并告警，不让一个坏条目废掉整份预设（`:273-274`）。

**（4）思考模式 → 采样默认值联动**（`:309-314`）：

```ts
// src/core/config.ts:310-315
  const thinkingKey: "on" | "off" = out.think === "on" ? "on" : "off";
  const presetSampling = SAMPLING_BY_THINKING[thinkingKey];
  if (src["temperature"] === undefined) out.temperature = presetSampling.temperature;
  if (src["top_p"] === undefined) out.top_p = presetSampling.top_p;
  if (src["presence_penalty"] === undefined) out.presence_penalty = presetSampling.presence_penalty;
```

条件都是 `src[...] === undefined` —— **只填用户没写过的字段**。两套推荐值的出处是 `:75-81`
（思考模式下 presence 给高了会中英混杂）。

**（5）生成上限**（`:319-325`）：开思考时下限抬到 16384；`max_predict >= context` 时告警「上限会失效」。
**（6）V cache 量化依赖 Flash Attention**（`:327-332`）与**（7）推测解码一致性**（`:335-337`）：
FA 关了就退回 `f16`（只压 K）；`spec_type` 是 `draft-*` 却没草稿模型就告警。

### 3.3 归一化之后：哪些字段一定有值，哪些可能为空

这是最容易想当然的一处：**只有被上面那些分支显式碰过的字段才有类型保证**，其余从 `...src`
展开而来，值可以是任意类型。我实测跑过一次（`node --input-type=module -e` 直接 import 这个 `.ts`
文件 —— 项目没有编译步骤，Node 原生类型擦除就能跑），输入 `{ llama_dir: 'X', main_model: 5,
temperature: 'abc' }`，输出里的关键值是：`context=32768`、`max_predict=16384`、`port=8080`、
`host="127.0.0.1"`、`think="off"`、`mode="single"`、`top_p=0.8`、`temperature=null`、
`repeat_penalty=null`、`llama_dir="X"`、`main_model=5`、`models_dir=undefined`、`threads=null`。结论分三类：

- **一定有值**：`port` / `host` / `mode` / `think` / `max_predict` / `presets`
  （空表的理由见 `src/core/config.ts:61-62`：形状稳定，界面判断「有没有预设」不必再判 `undefined`）。
- **一定是数字，但可能是 `null`**：`context` / `threads` / `batch_size` / `parallel` / `models_max` 等
  （`:213-221`）。这里的 `null` 是**有意义**的，表示「交给 llama.cpp 自己定」。
- **没有类型保证**：`llama_dir` / `main_model` / `models_dir` / `server_exe` / `spec_type` /
  `custom_args` / `extra_env` 这些**没被归一化碰过**的字段 —— 上面那次 `main_model: 5` 就原样留成了数字。
  （为什么这样也能跑，是拼装层的事，见 [05 参数拼装与决策表](./05-参数拼装与决策表.md)。）

还有一个反直觉结论：`temperature: 'abc'` 得到 `null` 而**不是**官方推荐值 —— 联动分支只看
`src["temperature"] === undefined`，写非法值也算「你写过」（`:312`）。这类边界在 `:229-238`。

### 3.4 写回：`saveConfigFile` 为什么关心键的顺序

`preferred` 是一张手写的键名清单（`src/core/config.ts:375-427`），从 `llama_dir` 排到 `custom_args`。
写入分两轮（`:428-434`）：先按清单顺序放**有值**的键，再把剩下的追加在后面，最后
`writeFileSync(path, `${JSON.stringify(ordered, null, 2)}\n`, "utf8")`：

```ts
// src/core/config.ts:429-430
    if (config[key] !== undefined) ordered[key] = config[key];
  }
```

动机在 `src/core/config.ts:363-364`：「**键顺序稳定**：先按 `preferred` 列表输出，再把剩下的键
追加在后面。这样同一份配置反复保存不会产生满屏无意义的 diff，人肉 review 也舒服。」
另外「保留下来的 `null` 是有意义的，表示"交给 llama.cpp 自己决定"」（`:366-367`）。

实测（临时目录 + `node`，输入 `{...DEFAULT_CONFIG, 某个没建模的键: '值', port: 8001,
server_exe: undefined, threads: null}`）：没有 BOM；键序从 `llama_dir,mode,presets,models_max,host,port`
一直到 `custom_args`，接着 `mlock,no_mmap,no_warmup,no_webui,metrics`，最后才是 `某个没建模的键`；
`threads` 值为 `null` 被写出，`server_exe` 完全没出现。三种现象都能解释：`port` 在 `host` 之后
是清单顺序；`mlock` 等五个键**不在** `preferred` 里（对比 `:375-427` 与 `:64-72`），按
`DEFAULT_CONFIG` 的插入顺序落在后面；未知键不在清单里，排最后。

**顺序稳定对用户的意义**：打包后那份配置就在 exe 旁边，是明确鼓励直接用编辑器改的。
固定键序让「保存一次」只改真的变了的行，也让 git 里的 diff 是给人看的。

### 3.5 落点三选一：`resolveAppDir` / `isDirWritable` / `chooseDataLayout`

先是「应用目录」—— 它不是简单的 exe 所在目录：

```ts
// src/main/paths.ts:46-56
export function resolveAppDir(input: ResolveAppDirInput): string {
  const portable = input.portableExecutableDir?.trim();
  if (portable) {
    try {
      return resolve(portable);
    } catch {
      // 环境变量给了非法路径：静默退回 exe 目录 —— 宁可落到临时目录，也不能因此起不来
    }
  }
  return dirname(input.exePath);
}
```

原因（`src/main/paths.ts:36-41`）：单文件便携版每次启动都把自己解压到 `%TEMP%\<随机名>\`，
`app.getPath("exe")` 指的就是那个临时目录。`.trim()` 也有用例兜着：空串与纯空白都退回 exe 目录
（`src/test/paths.test.ts:96-100`）。

再是「能不能写」：`isDirWritable`（`src/main/paths.ts:67`）**真的写一个探针文件**
`.llama-launcher-write-probe` 再删掉（`:68-76`），任何异常都返回 `false`（`:77-91`）——
理由在 `:60-61`：「只看权限位在 Windows 上并不可靠（ACL、只读介质、网络盘的表现都不一样）」。

最后是决策本体（`src/main/paths.ts:135`）：打包 + 可写时走这段，另外两种情形见后面两句：

```ts
// src/main/paths.ts:146-152
  if (canWrite(input.exeDir)) {
    return {
      portable: true,
      configPath: join(input.exeDir, PORTABLE_CONFIG_NAME),
      dataDir: join(input.exeDir, PORTABLE_DATA_SUBDIR),
    };
  }
```

开发模式（`:138-144`）配置放 `input.projectDir`、`dataDir` 用 `input.defaultUserDataDir()`；
只读时（`:154-159`）`const fallback = input.defaultUserDataDir();`，配置与数据都退回 `fallback`。
两个常量是 `PORTABLE_DATA_SUBDIR = "data"`（`:17`）与 `PORTABLE_CONFIG_NAME = "llama-launcher.json"`（`:20`）。
`canWrite` 可注入是刻意的（`:104`），只读场景在测试里才好造。

**判定边界（全部来自 `src/test/paths.test.ts`）**：开发模式配置在项目根目录、`dataDir` 用默认 userData
（`:20`）；打包 + 可写 → `portable: true`，配置与 `data/` 都在 exe 旁（`:32`）；打包 + 只读 → 退回
userData（`:46`）；不注入 `canWrite` 时真探测也判为可写（`:59`）；探针必须清理干净（`:8`）；
**目录不存在返回 `false` 且不抛异常**（`:16`）；目录里已有文件和子目录不影响判定（`:72`）。
最后一条最容易忽略：「目录不存在」= 不可写 —— 所以打包后若 `exeDir` 不存在，会直接走只读回退分支
（第 5 节练习 3 的考点）。

### 3.6 惰性求值的 `defaultUserDataDir`

注释的原话（`src/main/paths.ts:115-117`）：「⚠ 必须是**惰性**的（传函数而不是字符串）：
`app.getPath("userData")` 这个调用本身会把目录建出来（实测确认）……一旦在决定之前就调用它，
`%APPDATA%\<应用名>` 就会留下一个空目录。」主进程照这个约定接线：
`defaultUserDataDir: () => app.getPath("userData")`（`src/main/index.ts:80`），
而 `app.setPath("userData", ...)` 必须在 `app.whenReady()` 之前做完（理由 `src/main/index.ts:66-71`）。

### 3.7 `schema` → `SchemaEntry` → 控件：一份声明怎么变成表单

链路上有四段，数据只往一个方向流：

1. **声明**：`PARAM_SPECS`（`src/core/schema.ts:43`）、分组 `PARAM_GROUPS`（`:19-29`）、
   反查表与访问器（`:328`、`:336-338`）。
2. **探测支持情况**：`resolveSpecs()` 用当前能力逐条问「这个参数你认吗、实际用哪个名字」（`:350-358`）。
3. **打包成 IPC 载荷**：`buildSchemaPayload()`（`src/main/payload.ts:36`）把 spec 与探测结果合成
   `SchemaEntry`，并补上 `supported` / `resolvedFlag` / `takesValue` / `deprecated`（`:57-70`）。
   其中 `supported` 是**三态**：`caps === null` 表示还没跑过 `--help`，界面显示「未探测」，
   而不是乐观地当成支持（`src/main/payload.ts:30-31`）。
4. **渲染控件**：`controlFor()` 把 `kind` / `enumValues` 映射成控件，判定顺序是
   `bool` → 有 `enumValues` → `int`/`float` → 兜底文本框
   （`src/renderer/src/components/ParamsForm.tsx:44-86`）：

```tsx
// src/renderer/src/components/ParamsForm.tsx:54-62
  if (entry.enumValues !== undefined && entry.enumValues.length > 0) {
    return (
      <Select
        value={typeof value === "string" ? value : ""}
        disabled={disabled}
        onChange={(next) => set(next === "" ? null : next)}
        options={[{ value: "", label: "（用 llama.cpp 默认）" }, ...entry.enumValues.map((v) => ({ value: v, label: v }))]}
      />
    );
```

外层按 `group` 归类并跳过由左侧「模型」面板负责的字段
（`src/renderer/src/components/ParamsForm.tsx:172-178` 配 `MODEL_PANEL_KEYS`，`:15-24`），
否则会出现「左边显示 A、右边显示 B」的假象（`:10-14`）。`hint` 不用额外接线，直接成为 tooltip（`:210`）；
状态徽标（本版本不支持 / 未探测 / 已废弃 / preset 接管）在 `Badges`（`:103-150`），
「preset 接管」只在参数**确实有值**时才显示（`:132`）。

**好处**：新增参数时维护约定只要求改一处（`src/core/schema.ts:34-39`）—— 在 `PARAM_SPECS` 加一条、
在 `LauncherConfig` 加对应字段、必要时填 `presetKey`，表单会自动多出一行，不写任何 JSX；
某个参数被新版 llama.cpp 改名，只需把新名字插到 `candidates` 前面。

## 4. 踩过的坑与设计取舍

> **1. 便携版每次启动配置都被重置。** 单文件便携版每次启动先解压到 `%TEMP%\<随机名>\`，
> `app.getPath("exe")` 指的是那里，下次启动目录名又不一样。修法是认 electron-builder 注入的
> `PORTABLE_EXECUTABLE_DIR`（`src/main/paths.ts:36-41`、`README.md:619-624`，这条路径有 4 个单测）。

> **2. `app.getPath("userData")` 这个调用本身会把目录建出来。** 早先在「决定落点」之前就调它取默认值，
> 结果便携模式下也在 `%APPDATA%` 里留了个空目录。见 `src/main/paths.ts:114-117`、
> `src/main/index.ts:72-74`、`README.md:686-688`。

> **3. 开发态与打包版读的是两份不同的配置文件。** `README.md:571-573`：「**开发模式（`pnpm dev`）
> 与打包版读的是两份不同的配置** —— 前者用项目根目录的 `llama-launcher.json`，后者用 **exe 旁边**那份。
> 改了一份却发现"打包版没变化"，多半就是改错了文件（这个坑也踩过）。」
> 代码上这就是 `chooseDataLayout` 的第一个分支（`src/main/paths.ts:138-144`）；排查办法是看界面上
> 显示的 `configPath`，它就是真正在用的文件（`src/main/index.ts:146`）。

> **4. 输入框里的灰色文字只是 `placeholder`，不是值。** `README.md:646-651`：「输入框里有行灰色的
> `placeholder`（当时写死成 `E:\Code\llama\models`），看着像默认值、其实不是值 —— 于是"明明有默认值
> 为什么还报警"就成了必踩的坑。」现在灰字改成不具误导性的提示（对文本框来说就是该参数的 CLI 名字，
> `src/renderer/src/components/ParamsForm.tsx:82`），并在**确实探到**候选路径时给一个可点的「填入」
> 按钮（候选来自 `src/main/session.ts:259-270`，只报告确实存在的东西，`:255`）。判断方法在
> `src/main/session.ts:251-252`：**灰字就是没设置，黑字才是真写进去了。**

> **5. 写文件必须 UTF-8 且不带 BOM。** BOM 会让下游（llama-server 读 presets.ini 时）直接解析失败
> （`src/core/config.ts:360-362`）；`src/test/config.test.ts:190` 断言首字符不是 `0xfeff`。

> **6. 首次运行刻意做成「生成 → 重新读一遍」。** 生成完立刻 `loadConfigFile` 读回来当当前状态
> （`src/main/session.ts:196-213`），这样「首次运行的内存状态」与「第二次启动读文件的状态」完全一致
> （`:165-166`）。打包前清空产物目录也会连配置一起删掉，这是「改了没生效」的另一种成因，
> 现在由 `scripts/package.mjs` 构建前备份、构建后放回（`README.md:552-557`，
> 详见 [10 测试、打包与发布](./10-测试-打包与发布.md)）。

## 6. 自测题

**第 1 题**：为什么 `llama_dir` 在类型上必填、其余字段可选？运行时这两件事的实际差别是什么？

<details>
<summary>第 1 题答案</summary>

必填是类型层面的表达：`llama_dir` 是整条启动链路的锚点。但它的默认值是空串
（`src/core/config.ts:30`），所以运行时「必填」不等于「一定有值」—— 空串表示「还没探到」，
由 `discoverLlamaDir`（`src/core/config.ts:473`）和 `discoverModelLayout`（`:563`）自动探测去填。
其余字段可选，是因为配置允许手写：只写一个 `port` 也能跑，缺的由 `DEFAULT_CONFIG` 兜底（`:193`）。

</details>

**第 2 题**：配置里写 `"temperature": "abc"`，归一化之后 `temperature` 是什么？为什么不是官方推荐值？

<details>
<summary>第 2 题答案</summary>

是 `null`。联动分支的条件是 `src["temperature"] === undefined`（`src/core/config.ts:312`）——
写了非法值也算「你写过这个字段」，所以不填推荐值；类型收敛把它转成了 `null`（`:229-238`）。
`null` 在三值约定里表示「不传，让 llama.cpp 用自己的默认值」（`src/core/types.ts:111-112`）。

</details>

**第 3 题**：给 `PARAM_SPECS` 加一条新参数，界面会自动出现控件吗？还要改哪些文件？

<details>
<summary>第 3 题答案</summary>

会自动出现。表单是遍历 `PARAM_SPECS` 生成的（`src/renderer/src/components/ParamsForm.tsx:173` 起），
控件类型由 `kind` / `enumValues` 决定（`:44-86`），`hint` 自动成为 tooltip（`:210`），渲染层不用改。
还要动的是：`LauncherConfig` 加对应字段（否则存不进配置）、必要时填 `presetKey`
（`src/core/schema.ts:34-39`），以及让拼装层认识这个键
（[05 参数拼装与决策表](./05-参数拼装与决策表.md)）。完整走一遍是
[11 实战：加一个新参数](./11-实战-加一个新参数.md)。

</details>
